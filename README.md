# PHASOR — 엣지 통합 메모리에서 Out-of-Core MoE LLM 서빙

**PHASOR: Phase-Aware Expert Residency and Staging for Out-of-Core MoE Serving on
Unified-Memory Edge Devices**

(이전 이름 LEDGER. 코드와 결과 파일의 `ledger` 표기는 PHASOR의 상주 정책을 가리킨다.)

**플랫폼:** NVIDIA Jetson AGX Thor · JetPack 7.2 / L4T R39.2 · CUDA 13.0 · Blackwell sm_110
· 122.8 GiB 통합 coherent 메모리 · WD SN5000S 1 TB NVMe (PCIe Gen4 x4) · **swap 없음**

> **위상별로 다른 수단.** MoE 서빙의 전문가 접근은 재사용 구조가 다른 두 위상으로 되어 있다.
> 프리필은 프롬프트 합집합(층당 약 80%)을 요청당 한 번 읽고, 디코드는 토큰마다 층당 k개를
> 읽는다. 예산이 합집합보다 작으면 어떤 상주 정책도 프리필 읽기량을 바꾸지 못하므로
> (§4.3), PHASOR는 두 위상을 다른 수단으로 다룬다. **디코드**는 상주로 — 각 (층, 전문가)의
> 가치를 다음 디코드가 그것을 쓸 확률로 추정하고(최근성과 디코드 이력), **프리필**은 스테이징으로 — 복사 없는 스테이징이 데이터 경로의 발자국을
> 선언한 윈도우로 묶어 남는 용량을 상주에 돌려주고, 층 단위 파이프라인과 배칭이 프리필 읽기를
> 연산 뒤로 숨기거나 요청 간에 공유한다.

> **요약.** 통합 메모리 엣지 장치에서는 CPU와 GPU가 하나의 메모리 풀을 쓴다. 호스트 메모리가
> 크다는 기존 오프로딩 시스템의 전제가 성립하지 않고, 호스트 스테이징은 상주와 같은 예산을
> 두 번 쓴다(pread+copy 2.18x, cuFile 5.31x, PHASOR 1.17x). 모든 시스템을 자기 데이터 경로로,
> 같은 cgroup 메모리 상한 아래에서 같은 프롬프트로 비교하면, Qwen3-30B-A3B LongBench에서
> PHASOR는 가장 가까운 재현 SOTA보다 요청 시간 1.11–1.27x, TPOT 1.74–2.11x 빠르고
> llama.cpp보다 요청 시간 6.3x 빠르다(§4.2, 실험 진행 중).

**도메인.** 메모리 예산이 제약된 coherent 엣지 SoC 위의 **배치형 out-of-core MoE 서빙**.

## 1. 서론

### 1.1 문제 설정 — 연산은 충족되고 메모리는 부족하다

Qwen3-235B-A22B는 총 2350억 파라미터인데 토큰 하나를 만드는 데 **220억 개만** 쓴다.
Jetson AGX Thor가 그 연산을 하는 데 걸리는 시간은 **0.89 ms**다. 연산 측면에서는 여유가 있다.

제약은 메모리다. Q4_K_M으로 양자화해도 **132.4 GiB**이고 기기에는 **122.8 GiB**가
있다. 8% 모자란다.

서버 환경에서는 해법이 단순하다. 메모리를 더 사거나 GPU를 늘려 샤딩한다. 엣지 환경에서는 어느 쪽도 불가능하다 — 메모리가 고정이고, CPU와 GPU가 **같은 풀을 공유**하며, **swap이 없어 초과는 느려짐이
아니라 OOM이다.** 그래서 가중치의 일부는 반드시 스토리지에 남고, 필요할 때 읽어 와야 한다.

**엣지 MoE 서빙은 연산 문제가 아니라 데이터 이동 문제다.**

### 1.2 선행연구의 접근 — 디코드 시점의 예측과 캐싱

모델이 메모리보다 클 때 무엇을 할 것인가에 대해 MoE 관련 선행연구는 하나의 접근으로 수렴한다 — **전문가 활성화가 희소하니, 어느 전문가가 필요할지 맞히거나 인기 있는
것을 캐싱하라.**

| 갈래 | 대표 | 하는 일 |
|---|---|---|
| 예측 | Pre-gated MoE, SiDA-MoE, ProMoE | 게이팅을 앞당기거나 해시로 다음 전문가를 맞힌다 |
| 캐싱 | MoE-Infinity, HOBBIT, Klotski, Mixtral-offloading | 최근·자주 쓰인 전문가를 남긴다 |
| 연산 배치 | Fiddler | 가중치를 옮기는 대신 CPU에서 계산한다 |
| 압축 | EdgeMoE, 양자화 | 전문가를 줄여 더 담는다 |

네 갈래가 겨냥하는 것은 **모두 디코드다** — 다음 토큰이 쓸 전문가를 준비하는 일.
디코드가 토큰마다 반복되므로 최적화 표면이 거기에 있다는 판단에 근거한다.

### 1.3 라우팅 실측 — 위상별 I/O 비대칭

우리는 Qwen3-30B-A3B의 라우터 48개에 훅을 걸어 모델이 **실제로 고른** 전문가를
59,520회 기록했다(§2.3). 결과는 위 전제와 일치하지 않는다.

층별 인기순으로 전문가의 88%를 상주시키면:

| 위상 | 미상주 접근 | I/O | 연산 | 무엇이 지배하나 |
|---|---:|---:|---:|---|
| **디코드** (토큰당) | 확률질량 **0.06%** | **0.2 ms** | 0.89 ms | **연산 바운드 4.4x** |
| **프리필** (613토큰) | 합집합 미스 **8.0/128** | **1460 ms** | 545 ms | **I/O 바운드 2.7x** |

**상주가 충분하면 디코드는 I/O 바운드가 아니다.** 토큰당 0.2 ms는 연산 0.89 ms 안에 들어간다.
남는 것은 프리필이고, 그 I/O는 뒤따르는 613토큰 디코드 전체의 **15배**다.

이유는 두 위상이 읽는 것이 다르기 때문이다. 디코드는 토큰마다 8/128(6.25%)을 읽는데
그것이 인기 있는 쪽에 몰려 있어 상주로 거의 덮인다. 프리필은 프롬프트 전 토큰의
**합집합**을 읽으므로 **인기 없는 전문가까지 건드린다** — 613토큰이면 층당 79.3%다.

### 1.4 프리필에서 선행 기법이 무효인 이유

최적화 대상을 프리필로 옮기는 것만으로는 해결되지 않는다. §1.2의 네 갈래는 프리필에서
구조적으로 적용되지 않는다.

| 갈래 | 프리필에서 |
|---|---|
| **예측** | **예측 대상이 없다.** 합집합이 결국 전부 접근된다 |
| **캐싱** | **재사용이 없다.** 각 전문가를 1회만 읽는다 |
| 연산 배치 | 프리필의 연산량이 커서 CPU로 이전할 수 없다 |
| 압축 | 유효하나 직교한다 |

캐싱 계열에는 추가로 다음 측정이 적용된다. 한 층 안에서는 상위 절반이 트래픽의 **90.2%**를
먹는데, **어느** 전문가가 인기인지는 층마다 달라 전역으로 합치면 **58.4%** 로 거의
균등해 보인다(§2.3a). **전역 최근성이나 전역 인기로는 이 구조가 보이지 않는다.**

### 1.5 문제의 재정식화 — 메모리 분할

M > B이므로 통합 풀 B를 셋으로 쪼개야 한다.

```
B (122.8 GiB) = R (상주 가중치) + W (스테이징) + K (KV 캐시 / 배치)

프리필 I/O = (프롬프트 합집합 − R) / 전달 대역폭
```

W는 모델의 **0.9%에서 포화한다**(§A4.14) — 그 이상은 전부 R에서 차감된다. 따라서
층 1(데이터 경로)의 일은 **W를 최소로 유지하면서 장치 대역폭을 다 쓰는 것**이고,
남는 질문은 다음 하나다:

> **R을 무엇으로 채울 것인가.**

### 1.6 제안 — 프리필은 스테이징으로, 디코드는 상주로

교체 정책은 **하나의 접근 스트림**을 가정하고 그 안에서 최근성(LRU)이나 빈도(LFU)로
순위를 매긴다. MoE 서빙의 스트림은 **재사용 구조가 다른 두 위상**이다. 프리필은
합집합(Qwen3-30B 73–84%, Mixtral 98%, 235B 99%)을 요청당 한 번 건드리고, 디코드는 토큰마다
층당 k개를 건드린다. 예산이 합집합보다 작으면 프리필 읽기량은 어떤 상주 정책에서도 같다
(모든 상주 유닛이 다음 합집합에 포함되므로). 따라서 두 위상에는 다른 수단이 필요하다.

- **프리필의 비용은 스테이징이 줄인다.** 통합 메모리에서 데이터 경로의 스테이징 사본은
  상주와 같은 예산을 쓴다. 복사 없는 스테이징은 발자국을 선언한 윈도우의 1.17배로 묶어
  남는 용량을 상주에 돌려주고, 층 단위 파이프라인이 읽기를 연산 뒤로 숨기며, 배칭이
  합집합을 요청 간에 공유한다.
- **디코드는 상주가 줄인다.** 상주 유닛의 가치를 **다음 디코드가 그 유닛을 쓸 확률의
  추정치**로 두고 최근성과 디코드 이력의 합으로 계산한다. 유닛은 이미 윈도우로 읽힌 뒤에
  승인되므로 승인 비용은 복사뿐이고, 새 유닛은 축출 후보보다 가치가 클 때만 승인한다(§3.4).

### 1.7 PHASOR

```
Residency (디코드) — 디코드 사용 확률 추정 기반 상주
   V(u) = 최근성 + 디코드 이력 빈도
   선택적 승인: 가치가 축출 후보보다 클 때만 (윈도우에서 복사, 추가 읽기 없음)
   축출: 최소 가치, 단 현재 토큰이 쓰는 유닛은 제외

Staging (프리필과 전달) — gTier 데이터 경로
   착륙지가 곧 GPU 포인터 (복사 0회), 발자국 = 선언 윈도우의 1.17x
   정확 인출 — 증폭도 병합도 하지 않는다
   연속 제출 — 인출 사이에 큐를 비우지 않는다
   층 단위 파이프라인 — 다음 층 전문가를 읽는 동안 현재 층을 연산한다
   배칭 — 배치 안 프롬프트 합집합과 디코드 스텝의 필요 집합을 한 번만 읽는다
```

라우팅 일치로 공유 프리픽스를 식별해 그 합집합을 핀하는 기능(§3.5)은 구현돼 있으나 기본
구성에서 뺐다. 평가 워크로드에서 효과가 ±1% 이내였고, 배치에서는 같은 패밀리 요청이 한
배치에 모이면 핀된 합집합이 상주 용량을 채워 오히려 느려졌다(`--prefix-pin`으로 켠다).

층 1이 존재하는 이유도 §1.5에서 나온다. 데이터 경로가 선언보다 많은 메모리를 쥐면
그 초과분은 R에서 나오고, R은 프리필 읽기량이다. 측정하면 선언 2.00 GiB에 대해
gTier가 **2.33 GiB(1.17x)**, cuFile이 **10.62 GiB(5.31x)** 다 — 그리고 그 차이는
상주율 6.3%p, 다시 TTFT 0.66 s로 번역된다(§A4.15).

### 1.8 기여

1. **라우팅 구조의 측정.** 실제 모델의 라우터를 훅해 59,520개 결정을 기록하고 세 가지로
   분해했다 — 층별 대 전역 편향(90.2% 대 58.4%), 순차 지역성(우연의 6.6배), 공유
   프리픽스의 라우팅 동일성(앞 30토큰 100%). **전역 인기 캐시가 왜 실패하는지**가
   여기서 나온다(§2.3).

2. **문제 재정의.** 현실적 상주율에서 **디코드는 연산 바운드가 되고 프리필만 I/O
   바운드로 남는다**(15배). 문헌이 최적화하는 위상이 싼 쪽이다. 그리고 프리필에는
   예측도 캐싱도 구조적으로 듣지 않는다(§1.3, §1.4).

3. **데이터 경로의 메모리 발자국이 TTFT로 번역됨을 보인다.** 통합 풀에서 데이터 경로가
   선언보다 더 쓰는 메모리는 상주율에서 나오고, 상주율은 프리필 읽기량이다 —
   cuFile 5.31x 발자국 → 상주율 −6.3%p → TTFT +0.66 s(§1.6).

4. **통합 메모리에서 발자국을 재는 방법론.** 세 계수기가 서로 다른 것을 센다. cgroup은
   `cudaMalloc`을 과금하지 않고, RSS도 못 보고, `cudaMemGetInfo`는 매핑된 호스트 메모리를
   중복 계수해 합산이 불가능하다. `MemAvailable` 하락폭만 일관된다. 그리고 예산을
   고정하지 않으면 결론이 뒤집힌다 — 같은 mmap-cpu가 0.607 ↔ 5.289 GiB/s다(§A4.15).

5. **PHASOR — 프리필 인지 상주.** 프리필이 어차피 계산하는 프롬프트 라우팅이 같은 요청의
   디코드 라우팅을 예측한다는 것을 보이고, 이를 최근성·디코드 이력과 합쳐 상주 유닛의
   가치(디코드 사용 확률의 추정치)로 쓴다. 누적 횟수 효용은 평가 대상 밖에서 센 초기값으로는
   LRU에 졌고(§3.4), 확률 추정으로 바꾼 뒤 세 워크로드 모두에서 LRU를 이긴다(Qwen3-30B,
   예산 25%: 토큰당 디코드 읽기 −6.5% / −9.3% / −47%).

6. **프리픽스를 라우팅에서 읽는다.** 공유 프리픽스 구간은 라우팅이 결정적으로 같으므로
   (앞 30토큰 100%), 일치율로 패밀리를 판정한다 — 실제 공유 1.00/0.99/0.98은 핀하고,
   이름만 비슷한 쌍 0.31은 거부하고, 공유 구간을 넘으면 0.83으로 **스스로 포기**한다.
   **공유 범위를 선언할 필요가 없다.** 기존 프리픽스 캐싱은 KV만 재사용한다(§3.5).

7. **음성 결과와 버린 것.** 연산 과잉은 쓸 수 없다 — 양자화된 가중치는 **1.023x**밖에
   압축되지 않는다. 스테이징 윈도우는 모델의 0.9%에서 포화하고 슬롯 크기는 무관하다.
   그리고 만들다 버린 휴리스틱 셋을 기록한다 — "프리필은 빈 공간만", "첫 접촉에 캐시 안 함",
   치환 히스테리시스. **전부 효용 함수가 대체하거나 역효과였다**(§3.6, §A4.12, §A4.14).

### 1.9 주장하지 않는 것

- **추론 엔진이 아니다.** 전달 계층과 상주 정책, 그리고 이를 요청 단위로 재는 서빙
  드라이버다. 전문가 FFN은 bf16에서 실제 커널로 실행할 수 있으나, 평가의 토큰당 연산 비용은
  같은 GGUF를 llama-bench로 잰 값을 쓴다(§4.1). 연산 비용은 모든 시스템에 같으므로 시스템
  간 차이는 I/O와 그 중첩에서 나온다.
- **상주로 프리필 I/O를 줄였다고 주장하지 않는다.** 예산이 프롬프트 합집합보다 작으면
  구조적으로 불가능하다(§4.3). 프리필 쪽 이득은 데이터 경로의 발자국, 층 파이프라인, 배칭에서
  나온다.
- **재현 베이스라인은 재현이다.** MoE-Infinity*, Mixtral-offloading*, FlashMoE*, DuoServe*는
  논문과 소스에서 정책과 데이터 경로를 옮겼고, 파이프라인은 이상적 중첩으로 계산해
  베이스라인에 유리하게 두었다(§4.1). 실제 엔진은 llama.cpp다.
- **235B의 연산 비용은 추정이다.** 적재할 수 없어 30B 측정값에 토큰당 접근 바이트 비를 곱했다.

## 2. 배경

이 절은 §1의 세 주장의 근거를 제시한다 — 왜 통합 풀이 문제를 다르게 만드는가,
왜 이 플랫폼에는 GDS가 없는가, 그리고 라우터가 실제로 무엇을 하는가.

### 2.1 통합 메모리 풀 — 가능성과 제약

Thor에서 `llama.cpp`는 이렇게 보고한다.

```
Device 0: NVIDIA Thor, compute capability 11.0, VMM: yes, VRAM: 125748 MiB
```

**시스템 RAM 전체가 VRAM이다.** 디스크리트 GPU를 전제한 오프로딩 시스템이 최적화하는
계층 — GPU 메모리와 호스트 DRAM 사이 — 이 사라진다. 여기까지는 알려진 이야기다.

덜 알려진 것은 그 다음이다. 두 계층이 합쳐지면서 **새로운 경쟁이 생긴다.**

| | discrete GPU | **Thor** |
|---|---|---|
| 모델 가중치가 사는 곳 | VRAM (희소) | 하나의 풀 |
| 스테이징 버퍼가 사는 곳 | 호스트 DRAM (풍부, 10배) | **같은 풀** |
| 둘이 경쟁하는가 | **아니오** | **예** |

디스크리트 GPU에서 FlexGen이 호스트에 큰 스테이징 버퍼를 잡아도 VRAM의 모델은 줄지
않는다. 여기서는 줄어든다. **모든 오프로딩 시스템의 설계가 이 전제를 상속하고 있다.**

Thor는 `pageableMemoryAccessUsesHostPageTables = 1` 인 최초의 Tegra이기도 하다.

| | discrete | **Thor** | Orin |
|---|---|---|---|
| `concurrentManagedAccess` | — | **1** | **0** |
| `pageableMemoryAccess` | — | **1** | **0** |
| GPU가 파일 백업 mmap 접근 | 불가 | **가능** | 불가 |

**기회.** `cudaHostAlloc(cudaHostAllocMapped)` 메모리는 **동시에** O_DIRECT DMA 대상이고
GPU가 직접 주소 지정하는 메모리다. 디스크리트 GPU에서는 이 둘이 서로 다른 메모리라
복사나 GDS가 필요한데 여기서는 같은 버퍼다. 그리고 추가 비용이 없다 — GPU가 그 메모리를
**254.0 GB/s**로 읽는데 `cudaMalloc` 메모리가 254.1이다
([`gtier/mapped_read_bw.cu`](gtier/mapped_read_bw.cu)). §3.2가 이것을 쓴다.
**Orin에서는 성립하지 않는다.**

**제약.** 같은 통합이 경쟁을 만든다. 데이터 경로가 잡는 모든 바이트가 R과 K에서 나오고,
**swap이 없으므로 초과는 느려지는 것이 아니라 OOM이다.** 얼마나 그러한지는 측정됐다 —
llama.cpp에 132.4 GiB 모델을 전부 GPU에 올리라고 하면 프로세스가 죽는 것이 아니라
**호스트가 재부팅된다. 5회 시도, 5회 재부팅**(§A4.16d).

### 2.2 장치 특성 — 병목은 링크가 아니라 SSD

| 항목 | 측정값 |
|---|---:|
| GPU STREAM-triad | 250.2 GB/s (이론치 273의 91%) |
| CPU + GPU 동시 | 230.3 GB/s (0.912x) |
| NVMe 링크 | PCIe Gen4 x4 = 이론 7.34 GiB/s |
| **NVMe 실측 최대** (fio 12설정) | **5.682 GiB/s** |
| bf16 연산 | 49.5 TFLOP/s |
| Swap | **0 B** |

Gen4 x4가 7.34 GiB/s를 나를 수 있는데 이 DRAM-less 드라이브가 5.68에서 막는다. 그리고
**동시성을 늘리면 오히려 느려진다** — 잡 1개 5.682, 4개 5.102. 단일 스트림 큐 깊이
64에서 이미 포화한다. 따라서 **병렬 읽기로 더 얻을 것이 없고**, 남는 여지는 무엇을
읽지 않을 것인가에 있다.

### 2.3 NVIDIA GDS는 이 플랫폼에 없다

```
cuFile driver: nvfs major=0 minor=0     ← nvidia-fs 커널 드라이버 없음
dstatusflags=0x0  →  GDS supported = 0  ← POSIX compat 모드 (바운스 버퍼)
```

Thor에서 cuFile은 `NVMe → 바운스 → cudaMemcpy → cudaMalloc 버퍼`이며 복사 제거 이점이
없다. 그리고 **그 바운스 버퍼는 호출자가 선언한 윈도우에 계산되지 않는다** — §1.7의
5.31배가 여기서 나온다. 버퍼 등록 자체에는 한계가 없다(64 MiB × 640 = 40 GiB 정상).

## 3. 설계

§1.5가 문제를 `B = R + W + K` 의 분할로 다시 썼다. 이 절은 그 분할을 순서대로 다룬다 —
먼저 **W를 작게 유지하면서 장치를 다 쓰는 법**(§3.2~3.3), 그다음 **R을 무엇으로 채울
것인가**(§3.4~3.5), 마지막으로 **약속한 예산을 지킨다는 것이 왜 성능 논증인가**(§3.7).

각 절의 구성은 동일하다 — **선행연구의 접근 → 이 플랫폼에서 성립하지 않는 지점 →
설계 → 측정된 이득.**

```
┌──────────────────────────────────────────────────────────────┐
│ 층 2 — 디코드 확률 추정 기반 상주                              │
│   § 3.4  V(u) = 최근성 + 디코드 이력                           │
│          선택적 승인, 최소 가치 축출                            │
│   § 3.5  (선택) 프리픽스를 라우팅 일치로 식별 → 핀              │
├──────────────────────────────────────────────────────────────┤
│ 층 1 — gTier 데이터 경로                                       │
│   § 3.2  착륙지가 곧 GPU 포인터 (복사 0회)                     │
│   § 3.3  정확 인출 + 연속 제출                                 │
└──────────────────────────────────────────────────────────────┘
                                         ▼  GPU가 직접 역참조
```

### 3.1 스테이징 윈도우 크기의 결정

스테이징 윈도우를 얼마로 잡을지는 설계가 아니라 측정으로 정해진다. 0.12 GiB에서
16 GiB까지 쓸면(§A4.14):

| 윈도우 | 모델 대비 | GiB/s |
|---:|---:|---:|
| 0.12 GiB | 0.2% | 3.669 |
| **0.50 GiB** | **0.9%** | **4.741** |
| 2.00 GiB | 3.5% | 4.830 |
| 16.00 GiB | 28.1% | 4.748 |

**0.5 GiB에서 포화한다.** 윈도우는 캐시가 아니라 **in-flight 버퍼**다 — 읽기가
도착하고, GPU가 읽고, 즉시 재사용된다. 다음 토큰에서 라우터가 다른 전문가를 선택하므로
보존할 이유가 없다.

따라서 W는 모델 크기를 따라갈 필요가 없고, **0.5 GiB 위의 모든 바이트는 R에서 훔친
것이다.** 층 1의 목표가 여기서 도출된다: 작은 W로 장치 대역폭을 포화시킬 것.

### 3.2 [층 1] 스테이징 — DMA 목적지와 GPU 주소의 동일성

**선행연구.** 스토리지에서 GPU로 가는 길은 둘이다. 호스트 버퍼에 읽고 복사하거나
(FlexGen, ZeRO-Infinity), GDS로 직접 DMA하거나(cuFile).

**깨지는 것.** Thor에는 GDS 커널이 없어(§2.3) cuFile이 바운스 버퍼로 퇴화한다 —
복사가 사라지기는커녕 **선언하지 않은 메모리가 붙는다.** 복사 경로는 복사 자체보다
**버퍼를 두 벌 확보한다는 점**이 문제다. 단일 풀에서는 그만큼 R이 줄어든다.

**설계.** `cudaHostAlloc(cudaHostAllocMapped)` 슬롯 하나가 동시에 O_DIRECT DMA 대상이고
GPU 주소다. 드라이브가 **GPU가 읽을 메모리에 직접 기록한다.**

```
discrete + GDS   NVMe ──DMA──▶ VRAM ──▶ GPU                       복사 0, 버퍼 1벌
Thor + cuFile    NVMe ─▶ 바운스 ─▶ cudaMemcpy ─▶ 버퍼 ─▶ GPU      복사 2, 버퍼 2벌+
Thor + pread     NVMe ─▶ 호스트 ─▶ cudaMemcpy ─▶ 디바이스 ─▶ GPU  복사 1, 버퍼 2벌
gTier            NVMe ──DMA──▶ cudaHostAllocMapped ──▶ GPU        복사 0, 버퍼 1벌
```

**이 선택의 비용.** 다음 가능성을 검토했다 — GPU가 매핑된 호스트 메모리를 자기 메모리보다
느리게 읽는다면, 복사를 아낀 만큼 가중치를 훑을 때마다 되갚는다. 디코드 토큰 하나가
3.4 GiB를 훑으므로 작은 차이도 크게 돌아온다. 측정 결과는
**매핑 254.0 GB/s, `cudaMalloc` 254.1, managed 258.3** 으로, 추가 비용이 없다.

**이득.** 선언 2.00 GiB 대비 실제 점유 **2.33 GiB (1.17x)**. pread+copy 4.35 (2.18x),
cuFile 10.62 (5.31x)(§A4.15). 복사가 사라지는 것은 대역폭이 아니라 **전송당 지연(~20 µs)**
이고 — 복사 대역폭 127 GB/s는 스토리지의 23배다 — **실질 이득은 버퍼를 한 벌만 잡는 것**,
즉 R에 그만큼을 더 배정할 수 있다는 점이다.

### 3.3 [층 1] 전달 — 정확 인출과 연속 제출

**선행연구.** 블록 단위로 읽고 남는 것은 버린다(페이지 캐시, mmap, 블록 캐시). 또는
인접 요청을 병합해 큰 I/O를 만든다.

**깨지는 것.** 이 장치의 대역폭-크기 곡선은 **선형도 단조도 아니다** — 랜덤 256 KiB가
1.179 GiB/s로 64 KiB의 4.311보다 느리다. 그래서 증폭은 거의 언제나 손해다(§A4.4).
그리고 **64 KiB 위에서 랜덤 ≈ 순차**(4.311 vs 4.203)이므로 병합할 이유가 없다(§A4.5).
전문가 텐서가 3 MiB이므로 이 워크로드는 그 위에 편안히 있다.

**설계 — 규칙 둘.**

- **고립된 범위를 증폭하지 않는다.** 곡선이 선형보다 느리게 자라므로 증폭이 언제나
  이득을 앞지른다.
- **인접 범위도 병합하지 않는다.** 깊은 큐에서 요청 발행 비용은 무시할 수 있고 전송 바이트만이 비용이다.

임계값은 모델이 아니라 측정으로 정한다 — 파라메트릭 모델(고정 요청비용 + 바이트당 비용)로
유도했다가 틀렸고, 지금은 후보 임계값들로 실제 돌려 최선을 고른다.

**설계 — 연속 제출.** `gtier_fetch`는 제출 후 전부 기다려 **인출 사이에 큐가 0으로
비워진다.** 티켓 기반 `submit`/`wait`이 다음 배치를 먼저 내보내고 이번 것을 거둔다.
티켓은 겹치지 않는 슬롯을 소유하고, CQE의 `user_data`에 티켓 id를 실어 다른 티켓의
완료를 만나도 잃지 않는다.

```c
gtier_ticket t0, t1;
gtier_submit(g, r0, n, &t0);
for (;;) {
    gtier_submit(g, r1, n, &t1);       // 다음 배치를 먼저
    gtier_wait(g, &t0, dev);           // 그다음 이번 것을 거둔다
    consume(dev);
    std::swap(t0, t1);
}
```

**이득.** 증폭 1.00x를 유지하면서 얕은 큐에서 **+31.7%**(배치 8). 서빙 전체로 보면
프리필 I/O **−11.8%**, 요청 시간 **−9.1%** 다 — **이득이 프리필에 집중되는 것은 예상과
일치한다.** 프리필은 합집합을 깊은 큐로 제출하므로 배치 경계가 많고, 디코드 토큰의
미스 수는 링을 비울 만큼 많지 않다.

### 3.4 [층 2 · PHASOR의 핵심] 위상 인지 효용

**선행연구.** 교체 정책은 **하나의 접근 스트림**을 가정하고 그 안에서 최근성(LRU)이나
빈도(LFU)로 순위를 매긴다. MoE 전문가 캐싱도 같은 형태다.

**깨지는 것.** MoE 서빙의 스트림은 **재사용 구조가 다른 두 위상**이다.

| | 프리필 | 디코드 |
|---|---|---|
| 건드리는 것 | 합집합 (층당 79.3%) | 토큰당 8/128 (6.25%) |
| 재사용 | 요청당 **1회** | 토큰마다, 인기 쪽에 몰림 |

하나의 척도는 이 둘을 구분하지 못한다. LRU는 프리필 접근을 최근 것으로 보고 디코드
작업집합을 밀어내고, LFU는 한 번 쓰인 프리필 유닛을 영영 들이지 않는다.

**설계.** 상주 유닛의 가치는 **다음 디코드가 그 유닛을 쓸 확률의 추정치**다. 디코드
라우팅을 예측하는 두 신호를 각각 [0, 1]로 정규화해 더한다.

```
V(u) = w_r · 2^(-age(u)/H)       최근성   (age: 서빙 스텝, H = 8, w_r = 1)
     + hd(u) / max hd            지금까지 관측한 디코드 라우팅 빈도
                                 u = (층, 전문가)
```

- **최근성**은 요청 안 연속 토큰의 재사용(층당 약 45% 공유)을 담는다. 반감기가 짧아
  LRU처럼 동작하되, 한 토큰 안에서 층을 1번부터 실행하는 순서 때문에 LRU가 앞쪽 층을
  체계적으로 내보내는 편향(§4.5)은 이력 항이 상쇄한다.
- **디코드 이력(`hd`)**은 요청 간에 되풀이되는 디코드 분포를 담는다. 프롬프트가 짧을수록
  강하다.
- **프롬프트 라우팅 항은 기본 구성에서 뺐다.** 현재 요청의 프롬프트 라우팅 빈도를 세
  번째 항(`a · pf_r / max pf_r`)으로 더하는 설계를 구현·평가했다. Qwen3-30B LongBench에서는
  프롬프트 상위 25%가 디코드 접근의 69.3%를 덮지만 Mixtral과 235B에서는 무작위 수준
  (25–35%)이고, 서빙 어블레이션에서 이 항을 넣으면 예산 0.25에서 세 워크로드 모두 0.9–1.8%
  느려지고 예산 0.45의 MMLU에서 4% 느려졌다(`--mix 0.5`로 켠다, §4.7).

**승인과 축출.** 유닛은 디코드든 프리필이든 이미 윈도우로 읽힌 뒤에 승인 여부가 정해지므로
승인 비용은 복사 한 번이다. 따라서 **새 유닛의 가치가 축출 후보(현재 토큰이 쓰는 유닛을
제외한 최소 가치 유닛, 프리픽스 핀을 켰다면 핀된 유닛도 제외)보다 클 때만** 승인한다.

**어떻게 여기에 왔는가 — 누적 횟수 효용의 실패.** 이전 설계는
`U(u) = h_prefill(u) + W·h_decode(u)`의 **누적 횟수**였고, 초기값을 평가 대상 트레이스에서
세고 있었다. 초기값을 같은 모델의 **다른 워크로드**에서 세도록 고치자(평가 대상의 미래를
정책에 알려주지 않도록) LRU보다 느려졌다(Qwen3-30B LongBench, 예산 25%: 요청 11.34 s 대
10.56 s, 토큰당 디코드 읽기 0.382 대 0.291 GiB). 누적 횟수는 빈도만 담으므로 방금 승인된
유닛이 곧바로 축출 후보가 되고, 다른 워크로드에서 인기 있던 유닛이 자리를 차지한다.
워크로드 간 초기 카운트는 옮겨지지도 않았다 — 시뮬레이션에서 MMLU 적중률을 0.777에서
0.680으로 낮췄다. 그래서 초기 카운트는 기본 구성에서 뺐다(`--profile-weight`로 ablation).

**상한과의 거리.** 트레이스 재생 시뮬레이터(Qwen3-30B, 상주 17.6%)의 디코드 적중률:

| 워크로드 | LRU | PHASOR | Belady (미래를 아는 최적) |
|---|---:|---:|---:|
| LongBench | 0.716 | 0.742 | 0.879 |
| ShareGPT | 0.658 | 0.693 | 0.840 |
| MMLU | 0.589 | 0.777 | 0.894 |

실제 드라이버(예산 4.35 GiB, 같은 조건)에서 토큰당 디코드 읽기는 LRU 대비 LongBench
−6.5%, ShareGPT −9.3%, MMLU −47%이고, 시뮬레이터 예측과 맞는다. Belady와의 격차는
남아 있다.

### 3.5 [층 2] 프리픽스 식별 (선택 기능, 기본 꺼짐)

> 기본 구성에서 뺀 이유는 §1.7에 있다. 아래는 기능의 설계다.

**관찰.** 라우팅은 은닉 상태의 결정적 함수이므로 공유 프리픽스 구간에서 **선택되는
전문가가 정확히 같다**(§2.4d). 기존 프리픽스 캐싱은 그 구간의 **KV만** 재사용한다.

**어떻게 쓰나.** 공유 프리픽스의 합집합은 같은 패밀리의 모든 요청이 프리필에서 다시
읽는다. 이 합집합을 핀하면 그 읽기가 사라진다. 두 가지가 필요하다.

**(a) 패밀리 판정은 이름이 아니라 라우팅 일치율로.** 같은 텍스트면 같은 전문가가
선택되므로, 프리픽스 구간의 라우팅 일치가 곧 증거다(임계값 0.90). 판정은 **온라인**이다.
첫 요청의 프리픽스 구간 라우팅을 기록하고, 이후 같은 이름 계열의 요청이 프리필을 마친
시점에 그 라우팅과 비교해 0.90 이상이면 패밀리로 확정하고 첫 요청의 합집합을 핀한다.
아직 서빙되지 않은 요청의 라우팅은 사용하지 않는다.

| 패밀리 | 일치율 | 판정 |
|---|---:|---|
| sysA / sysB / sysC (실제 공유) | 1.00 / 0.99 / 0.98 | **핀** |
| distinct (이름만 비슷) | 0.31 | 거부 |
| 공유 구간을 넘겨 65토큰까지 | 0.83 | **스스로 핀을 포기** |

**공유 구간의 범위를 명시할 필요가 없다. 라우팅에서 도출된다.**

**(b) 패밀리가 여럿일 때.** 실제 배포는 시스템 프롬프트를 하나만 사용하지 않는다. 상한을 넘으면
가장 오래 서빙되지 않은 패밀리를 축출하되 **그 패밀리가 단독으로 쥔 유닛만** 버린다.
1회만 등장한 패밀리는 핀하지 않는다 — 핀 비용을 지불하고 회수하지 못하기 때문이다.

### 3.6 제외한 휴리스틱 셋

다음 셋은 구현·측정했으나 **PHASOR에 포함하지 않는다.** 공통 원인이 있다 —
**모두 효용을 알 수 없을 때의 대체 수단이었고, 효용이 도입되자 불필요하거나 유해해졌다.**

**(a) "프리필은 빈 공간만 가져간다".** 효용이 없을 때는 옳다 — 프리필은 합집합을 한 번
읽고 돌아오지 않는데 순진한 캐시가 그것을 admit하며 디코드 작업집합을 쫓아낸다. 예산
16 GiB에서 토큰당 I/O가 369.91 → 121.45 ms다. **그러나 효용이 있으면 해롭다** —
프리필 히트를 세어놓고 그것이 작동하지 못하게 막으므로, 프롬프트가 반복해서 건드리는
유닛이 영영 상주하지 못한다(프리필 I/O가 1.343 s에 고정, 온전한 식은 0.594).

**(b) "첫 접촉에 캐시하지 않는다".** 한 번 스친 것으로 캐시가 차는 것을 막는 고전적
규칙인데 여기서는 역효과다 — 2회 요구 시 토큰당 I/O 5.50 → 14.03 ms. **승인되지 않은
디코드 작업집합은 카운트도 되지 않기** 때문이다.

**(c) 치환 히스테리시스.** 두 위상이 서로를 밀어내는 왕복을 막으려 했으나 거의 움직이지
않는다. 실제 왕복의 원인은 다른 곳에 있었다(§3.4의 인용 참조).

### 3.7 [층 2] 예산 계약

**선행연구가 약속하지 않는 것.** 오프로딩 시스템은 버퍼 크기를 설정으로 받지만 그것이
프로세스 총 점유의 상한이라고 약속하지 않는다. 디스크리트 GPU에서는 초과분이 풍부한
호스트 DRAM에서 나왔으므로 그래도 됐다.

**깨지는 것.** 하나의 풀에서 초과분은 R에서 나오고 R은 프리필 읽기량이다. 그리고
swap이 없으므로 **초과는 느려지는 것이 아니라 OOM이다** — cuFile은 8 GiB 예산에서
실행되지 않는다.

**설계.** gTier가 잡는 것은 슬롯 링 하나뿐이다(`slots × slot_bytes`). 상주 정책은 그 링
밖의 아레나를 쓰고, 비동기 티켓은 링을 `GTIER_MAX_INFLIGHT`등분해 쓴다. 선언한 것 외에
숨은 할당이 없다.

**계약이 지켜지는지 확인하는 법.** 계측기 셋이 서로 다른 것을 센다 — RSS는 `cudaMalloc`을
빠뜨리고, `cudaMemGetInfo`는 매핑된 호스트 메모리를 중복 계수하며, cgroup은 디바이스
메모리를 과금하지 않는다. `MemAvailable` 하락폭만 일관되다
([`scripts/memfoot.sh`](scripts/memfoot.sh), §A4.15).

**그리고 지키는 것이 TTFT다.**

```
발자국 1.17x → 상주율 88.0% → 프리필 8.3 GiB → TTFT 1.46 s   (gTier)
발자국 5.31x → 상주율 81.7% → 프리필 12.0 GiB → TTFT 2.12 s   (cuFile)
```

비교는 베이스라인 정책을 이 저장소의 데이터 경로 위에서 돌렸고 상주 초기값을 평가 대상
트레이스에서 셌으므로, 시스템 간 비교로 쓰지 않는다.

### 4.1 실험 구성

**질문.** 같은 요청을 같은 메모리 예산에서 처리할 때, 각 시스템이 자기 데이터 경로와
자기 정책으로 요청을 얼마나 빨리 끝내는가.

| 항목 | 값 |
|---|---|
| 장치 | Jetson AGX Thor, 통합 메모리 122.8 GiB, NVMe 5.68 GiB/s |
| 모델 | Qwen3-30B-A3B (17.3 GiB), Mixtral-8x7B (26.5 GiB), Qwen3-235B-A22B (132.4 GiB), 모두 Q4_K_M GGUF |
| 워크로드 | LongBench 21, ShareGPT 24 (다중 턴 11), MMLU 5-shot 24. **모든 모델에 같은 프롬프트**, 235B는 워크로드당 앞 8개 |
| 요청 | 프롬프트 최대 8192 토큰, 생성 32 토큰 (MMLU 8), greedy |
| 라우팅 | 각 모델을 실제로 실행해 캡처 (HF 훅 또는 llama.cpp `ffn_moe_topk`) |
| 예산 | 모델 바이트의 0.25 / 0.45 / 0.65 |
| 메모리 상한 | 모든 실행을 **예산 + 0.5 GiB** cgroup 안에서. pinned 호스트 메모리와 페이지 캐시가 모두 계산된다 |
| 반복 | 워크로드 2회 순회 (첫 순회는 콜드) |
| 연산 | 같은 GGUF를 전 층 GPU에 올린 llama-bench로 측정한 토큰당 비용. 235B는 적재 불가하여 30B의 값에 토큰당 접근 바이트 비(6.4)를 곱함 |

**비교 시스템.** 각 시스템은 자기 데이터 경로를 쓴다. `*`는 논문과 소스에서 정책과 경로를
옮긴 재현이다.

| 시스템 | 데이터 경로 | 상주 / 교체 | 층 파이프라인 | 배치 |
|---|---|---|---|---|
| LRU | 동기 pread → pinned 호스트 → 복사 | LRU | 없음 | 1 |
| MoE-Infinity* | O_DIRECT pread → pinned 호스트 → 비동기 복사 (`core/aio`) | 시퀀스 활성 집합 보존 + LRU | 있음 | 1, 4 |
| Mixtral-offloading* | 호스트 스테이징 → 복사 | LRU + 직전 토큰 투기 적재 | 있음 | 1 |
| FlashMoE* | 호스트 스테이징 → 복사 | 층별 고정 슬롯, FFN(1/recency, freq)이 축출 결정. Belady 레이블로 학습 | 있음 | 1, 4 |
| DuoServe-MoE* | 호스트 캐시 → 복사 | 호스트 LRU + 다음 층 top-k 예측 프리페치 (인기도 × 층간 친화도) | 있음 | 1, 4 |
| llama.cpp | 밀집 가중치는 GPU, 전문가는 mmap (`--cpu-moe`) | OS 페이지 캐시 | 엔진 자체 | 1 |
| **PHASOR** | gTier (복사 0회, 정확 인출, 연속 제출) | 디코드 사용 확률 추정 (§3.4) | 있음 | 1, 4 |

**공정성에 관한 가정.**
- 층 파이프라인이 있는 시스템은 모두 I/O가 연산 뒤로 이상적으로 숨는 것으로 계산한다
  (`max(io, c) + min(io, c)/L`). 프리페치 타이밍이 완벽하다는 가정이므로 베이스라인에
  유리하다.
- 복사 경로의 디바이스 스테이징(`cudaMalloc`)은 cgroup이 계산하지 않으므로, 측정한 발자국
  배수(pread+copy 2.18x, gTier 1.17x, §4.4)로 예산에서 뺀다.
- 학습·초기값이 필요한 정책(FlashMoE*, DuoServe*)은 같은 모델의 **다른 두 워크로드**로만
  학습한다. PHASOR는 초기값을 쓰지 않는다.
- Fiddler와 Mixtral-offloading 원본은 모든 전문가를 호스트 메모리에 둔다. 통합 메모리에서
  호스트와 GPU는 같은 풀이므로 모델 크기 미만의 예산에서는 실행되지 않는다
  ([`results/SOTA/PORTING.md`](results/SOTA/PORTING.md)). Mixtral-offloading의 정책은
  위의 재현으로 평가한다.

llama.cpp는 커밋 `be4a6a6` 빌드를 쓴다. 실행: [`scripts/stage3.sh`](scripts/stage3.sh), [`stage3b.sh`](scripts/stage3b.sh) (FlashMoE*),
[`stage3c.sh`](scripts/stage3c.sh) (DuoServe*). 전체 표:
[`results/MATRIX3/SUMMARY.md`](results/MATRIX3/SUMMARY.md).

### 4.3 이득이 어디서 나오는가 — 위상별 분해

요청 시간을 네 성분으로 나눈다. 아래는 모든 정책을 같은 데이터 경로에 올리고 파이프라인
없이 잰 값으로, 상주 정책만의 효과를 본다(Qwen3-30B, 예산 0.45, 초 단위).

| 워크로드 | 정책 | 요청 | 프롬프트 연산 | 프리필 I/O | 디코드 연산 | 디코드 I/O |
|---|---|---:|---:|---:|---:|---:|
| LongBench | LRU | 8.56 | 5.17 | 1.46 | 0.43 | 1.50 |
| | MoE-Infinity* | 8.46 | 5.17 | 1.45 | 0.43 | 1.40 |
| | PHASOR | 8.05 | 5.17 | 1.46 | 0.43 | **0.98** |
| ShareGPT | LRU | 3.94 | 0.53 | 1.13 | 0.43 | 1.86 |
| | PHASOR | 2.93 | 0.53 | 1.10 | 0.43 | **0.87** |

**상주는 프리필 I/O를 줄이지 못한다.** 예산이 프롬프트 합집합(층당 약 80%)보다 작으면 상주
유닛은 거의 모두 합집합 안에 있으므로, 어떤 유닛을 상주시키든 프리필 읽기량은 "합집합 −
상주 크기"로 같다. 프리필 비용을 줄이는 수단은 층 파이프라인(연산 뒤로 숨김), 배칭(합집합을
요청 간에 공유, §4.6), 데이터 경로의 발자국(상주 크기, §4.4)이다. 상주 정책이 바꾸는 것은
디코드 I/O이고, PHASOR는 이를 35–53% 줄인다.

최적(Belady)과 비교한다. 전체 표: [`results/SIM/SUMMARY.md`](results/SIM/SUMMARY.md).

| 모델 | 워크로드 | 상주 35%: LRU | LFU | PHASOR | Belady |
|---|---|---:|---:|---:|---:|

| | ShareGPT | 0.837 | 0.838 | **0.899** | 0.966 |

- PHASOR는 27개 조건 중 26개에서 LRU보다 디코드 미스가 적다(예외: 235B LongBench 14%,

  LRU보다 낫다.
- **Mixtral은 라우팅이 거의 균등해** 온라인 정책의 이득이 1–3%다(MMLU 제외). 이 모델에서
  시스템 이득은 상주가 아니라 데이터 경로와 파이프라인에서 나와야 한다.
- (프롬프트 항 포함 설정 기준) a = 0.5, H = 8은 상주 35%의 9개 조건 중 8개에서 각 조건의 최고 설정과 0.02
  이내다. 설정을 잘못 고르면 크게 떨어진다(235B MMLU 최저 0.693).

**라우팅 특성.**

| 모델 | 프롬프트 합집합 | 연속 토큰 공유 | 프롬프트 상위 25%가 덮는 디코드 |
|---|---:|---:|---:|
| Qwen3-30B | 72.8–83.5% | 42.5–48.3% | 61.6–69.3% |
| Mixtral-8x7B | 97.7% | 36.0–39.9% | 25.4–25.5% |
| Qwen3-235B | 99.0% | 43.5–49.9% | 30.4–34.7% |

프롬프트 합집합이 모든 모델에서 크므로 상주가 프리필 읽기량을 줄이지 못한다는 결론(§4.3)은
세 모델 모두에서 성립한다. 반면 프롬프트 라우팅의 디코드 예측력은 Qwen3-30B에서만 강하고
(무작위 25% 대비 62–69%), Mixtral에서는 없다. PHASOR의 이득은 주로 최근성과 디코드 이력의
결합에서 나온다.

### 4.6 배칭

정적 배칭은 배치 안 프롬프트의 합집합을 한 번 읽고, 디코드 스텝마다 배치의 필요 유닛
합집합을 한 번 읽는다. Qwen3-30B MMLU(예산 0.25)에서 요청당 프리필 읽기는 10.0 → 2.7
GiB로 줄고 처리량은 3.33 → 10.4 tok/s로 는다(PHASOR, 파이프라인). LongBench에서는 배치 안
프롬프트 연산이 누적되어 TTFT가 20 s가 되므로 처리량 이득이 없다(배치 1 5.20 대 배치 4 4.92
tok/s). 배치 4 비교(예산 0.45, LongBench): MoE-Infinity* 요청 30.18 s / 4.16 tok/s,
PHASOR 25.52 s / 4.92 tok/s.

### 4.7 어블레이션

진행 중 (Qwen3-30B, 예산 0.45, 세 워크로드). 끄는 항목: 층 파이프라인, 연속 제출, gTier →
pread+copy, 상주 정책 → LRU, 프롬프트 라우팅 항, 디코드 이력 항, 최근성 항, 누적 횟수 효용.

### 4.8 타당성 점검

- **정보 누수.** 초기 카운트를 평가 대상 트레이스에서 세면 누적 횟수 효용이 LRU를 크게
  이기지만(이전 판 §4.16e), 다른 워크로드에서 세면 LRU에 진다(요청 11.34 대 10.56 s).
  이 결과로 효용을 디코드 사용 확률 추정으로 바꿨다(§3.4). 학습·초기값이 필요한 베이스라인도
  같은 규칙으로 평가한다.
- **회귀.** 새 서빙 루프(배칭·파이프라인)는 배치 1, 파이프라인 없음에서 이전 루프와 토큰당
  디코드 읽기가 바이트 단위로 같다(0.2369 / 0.4392 GiB).
- **예산.** 모든 실행의 cgroup 최대 사용량을 결과 파일에 기록한다(`cgroup_peak_gib`).

## 5. 정직한 한계와 철회

- **전송 메커니즘의 우위는 큰 입도에서 좁다.** 1 MiB에서 cuFile 대비 1.28배, 4 MiB에서 1.16배다.
  LLM 가중치는 MiB 단위를 읽으므로 실제 운용 구간에서 격차가 작다. **레버는 전송이 아니라
  상주(최대 14x)와 덜 읽기(10x)에 있다.**
- **장치가 상한이다.** SSD 실측 최대 5.682 GiB/s(PCIe는 7.34까지 가능)이고 gTier는 97%에 있다.
  남은 3%는 비동기 경로가 티켓 2개만 써서 GPU 커널이 완전히 가려지지 않는 우리 쪽 결함이다.
- **철회: "cuFile이 큰 윈도우를 못 잡는다".** 직접 시험하니 **64 MiB 버퍼 640개, 40 GiB 등록이
  정상 동작한다.** 앞선 8 GiB 실패는 우리 벤치마크 설정 탓이었다.
- **철회: "비결정적 붕괴".** `ftruncate`가 만든 희소 파일 아티팩트였다
  ([`results/REGIMES.md`](results/REGIMES.md)).
- **정정: zero-copy는 대역폭이 아니라 지연 이득이다.** 복사는 전송당 고정비 ~20 µs이고
  coherent SoC에서 복사 대역폭(127 GB/s)은 스토리지보다 23배 빠르다.
- **철회: "mmap이 선언 윈도우의 6배를 쓴다".** RSS만 본 결과였다. 그 11.98 GiB는 **회수 가능한
  페이지 캐시**이고 커널이 압박받으면 돌려준다. 회수 불가능한 점유는 0.35~0.54 GiB로 전 백엔드
  중 가장 작다. mmap의 실제 약점은 메모리가 아니라, 예산이 조이면 대역폭이 4.535 → **0.607
  GiB/s**로 무너지는 것이다(§A4.15).
- **정정: pread+copy는 2.08이 아니라 4.35 GiB**(윈도우의 2.18배). 호스트 스테이징과 디바이스
  버퍼를 둘 다 잡는데 RSS가 후자를 못 본다. **cuFile은 4.04배가 아니라 5.31배**,
  **gTier는 1.04배가 아니라 1.17배**다 — 차이는 CUDA 컨텍스트 비용이고 모든 백엔드가 똑같이 낸다.
- **이 저장소의 벤치마크는 연산을 하지 않는다.** GPU 커널(`consume`)은 64바이트마다 한 바이트를
  더할 뿐 행렬곱도 어텐션도 KV 캐시도 없다. 따라서 보고하는 `tok/s`는 **"이 속도면 토큰당
  가중치를 이만큼 자주 댈 수 있다"**는 뜻이지 실제 추론 처리량이 아니다. 실제 추론은 여기에
  연산 시간이 더 붙는다.
- **탑티어 베이스라인 세 개를 모두 빌드했으나 아직 end-to-end 비교 측정은 하지 못했다.**
  MoE-Infinity는 `Qwen3MoeForCausalLM`을 지원하고 오프로드 저장소까지 구축되지만, 실행이
  네 번 죽었다. 원인은 순서대로 (1) `triton` 부재, (2) **sm_110 커널 부재** — `setup.py`가
  아키텍처를 sm_80/sm_90/sm_120으로 하드코딩해 `_store.so`에 sm_110 큐빈도 PTX도 없었고
  CUTLASS GEMM이 `Error Internal`로 실패했다(`MOE_CUDA_ARCHS` 환경변수를 받도록 패치하고
  PTX 폴백을 넣어 재빌드), (3) **이 기계의 IDE 언어 서버가 반복적으로 81 GB까지 부풀어
  전역 OOM을 일으킴** — 커널 로그의 OOM 네 건 중 세 건이 그것이고 벤치마크는 부수 피해였다,
  (4) cgroup 안에서 CUDA 컨텍스트가 `std::bad_alloc`. (3)을 막기 전에는 재실행해도 같은
  일이 난다.
- **PowerInfer와 FlexGen은 같은 모델로 비교할 수 없다.** 둘 다 Qwen3-MoE를 지원하지 않는다
  (PowerInfer는 자체 ReLU-sparsified GGUF, FlexGen은 OPT 계열만). 같은 파일 비교가 가능한
  것은 MoE-Infinity뿐이고, 나머지 둘은 각자의 네이티브 모델 위에서 돌리되 gTier를 그 동일
  파일에 겨누어야 한다. 모델은 받아두었다(PowerInfer-7B 15 GB, OPT-6.7B 38 GB).
- 빌드 절차와 네 가지 패키징 문제: 앞서
  "sm_110 PyTorch가 없어 불가능"이라고 적은 것은 틀렸다. 넷 다 패키징 문제였고 전부 해결됐다.
  절차는 [`scripts/baselines_setup.sh`](scripts/baselines_setup.sh)와
  [`scripts/torch_env.sh`](scripts/torch_env.sh)에 기록했다.
  - **PowerInfer**는 PyTorch를 쓰지 않는다 — llama.cpp 포크이고
    `-DCMAKE_CUDA_ARCHITECTURES=110`이면 그대로 빌드된다(CMakeLists 기본값이 52/61/70이라
    명시가 필요하다). CUDA 13, `libcublas.so.13` 링크 확인.
  - **PyTorch**: PyPI aarch64 휠이 CPU 전용인 것은 맞지만 NVIDIA Jetson AI Lab 인덱스에 CUDA
    빌드가 있다. `--extra-index-url`을 같이 주면 pip이 버전이 같은 PyPI 휠을 고르므로
    `--no-deps`로 그 인덱스에서만 받아야 한다. SBSA 휠이 NVPL과 cuDSS를 선언 없이 링크하므로
    둘을 `LD_LIBRARY_PATH`에 얹어야 한다. 결과: `torch 2.11.0`,
    `arch_list ['sm_110','sm_121']`, bf16 49.5 TFLOP/s.
  - **FlexGen**: 임포트 이름이 `flexgen`이 아니라 `flexllmgen`이다.
  - **MoE-Infinity**: `moe-store`가 별도 저장소(PyPI에 없음)이고 버전 핀이 어긋나며
    (`~=0.2.1` 요구, main은 `0.0.0` 빌드), CUTLASS 헤더가 번들되어 있지 않고,
    `/usr/local/cuda` 심링크가 13.2를 가리키는데 거기엔 `lib64/libcublas`가 없어
    `cannot find -lcublas`로 링크가 깨진다. 네 가지를 모두 고치면 C++/CUDA 확장 6개
    (`_store`, `_engine`, `_marlin`, `_kv_cache`, `_paged_attn`, `_v4_fp4`)가 정상 빌드된다.
- **PowerInfer는 out-of-core 체제에서 비교할 수 없다.** PowerInfer 형식 모델이 7B(14.11 GiB)와
  70B q4(39.28 GiB)뿐이고 둘 다 122.8 GiB DRAM에 들어간다. 다만 그 희소성 단위가 KiB급이라는
  것은 코드에서 확인된다 — `gpu_idx`/`gpu_bucket`과 `dequantize_mul_mat_*_sparse` 커널이
  FFN 가중치 행렬의 **행 단위**로 접근하며, LLaMA-7B는 모델 차원 4096이므로 한 행이 q4에서
  약 2 KiB다. §A4.4의 입도 바닥(64 KiB)보다 한참 아래다.
- **철회: "라우팅 인지가 10배 레버"(§A4.11 초판).** 상주 0을 가정한 값이었다. 층별
  인기순으로 88%를 상주시키면 디코드 I/O는 토큰당 0.2 ms로 연산(0.89 ms)보다 작아진다.
  이득을 주는 것은 라우팅 인지가 아니라 **상주율**이고, 남는 병목은 **프리필**이다(§A4.16).
- **철회: 초판 §1.5의 "8.3 GiB 초과가 읽어야 할 바이트를 53% 늘린다".** 토큰당 바이트가
  `(M−R)`에 비례한다고 가정했는데, 상주를 인기순으로 채우면 스트리밍되는 것은 인기 없는
  전문가이므로 접근 확률이 크기 비율보다 작다. 비율(1.45x)은 살아남았고 절대값이 틀렸다.
  현재 §1.6은 실측 라우팅으로 다시 계산한 값이다.
- **철회: "I/O가 연산의 2475배"(초판 §1.1).** 상주 0을 가정한 값이다. 상주 88%에서는
  디코드가 연산 바운드(4.4x)이고 프리필만 I/O 바운드(2.7x)다.
- **실측 라우팅 표본이 작다.** 프롬프트 6개, 디코드 384토큰, 기술 문서 도메인, greedy
  디코딩, 상주 순서를 디코드 통계로 사후 결정. **상주 효과는 상한에 가깝다.** 프리필/디코드
  비대칭은 표본에 둔감한 구조적 결과다.
- **§3.5(프리픽스 조건부 상주)와 §3.6(위상별 재분할)은 설계만 되어 있고 미구현이다.**
- **MoE 라우팅은 이제 토큰마다 다시 뽑는다**(§A4.13). 고치기 전 숫자는 페이지 캐시를 재고
  있었다. 다만 그 체제에서 캐시 정책은 **손해**다 — 적중률 47.2%인데 4 MiB 블록에 3 MiB
  전문가 텐서가 정렬되지 않아 증폭 1.24x가 붙고, 4.321 → 3.547 GiB/s로 느려진다.
- **`gtier_fetch`의 동기 경로는 여전히 큐를 비운다.** 비동기 API가 있지만 캐시 정책과는 아직
  결합되지 않았다(`gtier_submit`은 `GTIER_CACHE_NONE`만 지원).

## 7. 설치 및 사용

### 7.1 요구사항

- NVIDIA Jetson AGX Thor (JetPack 7.2 / L4T R39.2 이상), CUDA 13.0, `sm_110`
- `liburing-dev` (2.5 이상), `gcc`, `nvcc`
- O_DIRECT를 지원하는 파일시스템 위의 NVMe
- 페이지 캐시를 비우려면 passwordless `sudo` (측정 재현용)

```bash
sudo apt install -y liburing-dev
```

### 7.2 빌드

```bash
git clone git@github.com:changjongkim/thor_gtier.git
cd thor_gtier/lib
make                      # libgtier.a, gtier_bench, gguf_bench
make ARCH=sm_87           # 다른 Jetson 세대
```

### 7.3 라이브러리 사용

```c
#include "gtier.h"

gtier_config cfg = {0};
cfg.backend      = GTIER_BACKEND_GTIER;
cfg.slot_bytes   = 1 << 20;            // 측정된 최적 스테이징 크기
cfg.slots        = 64;
cfg.queue_depth  = 64;
cfg.merge_gap    = 0;                  // 측정 결과: 병합하지 않음
cfg.cache_policy = GTIER_CACHE_ADAPTIVE;
cfg.max_fetch_ranges = 32;

gtier *g = gtier_open("model.gguf", &cfg);

gtier_range r[32] = { {off0, len0}, {off1, len1} /* ... */ };
void *dev[32];
gtier_fetch(g, r, 32, dev);            // dev[i] 는 GPU가 바로 읽는 포인터
my_kernel<<<...>>>((const uint8_t *)dev[0], len0);
gtier_close(g);
```

**연속 배치를 내는 클라이언트는 비동기 API를 쓴다** — 큐를 비우지 않아 얕은 깊이에서 최대 31.7% 빠르다.

```c
gtier_ticket t0, t1;
gtier_submit(g, r0, n, &t0);
for (;;) {
    gtier_submit(g, r1, n, &t1);       // 다음 배치를 먼저
    gtier_wait(g, &t0, dev);           // 그다음 이번 것을 거둔다
    consume(dev);
    std::swap(t0, t1);
}
```

**제약.** 한 범위는 하나의 슬롯 안에 들어가야 한다. O_DIRECT 정렬이 양끝으로 최대 4 KiB씩
늘어나므로 범위 길이를 `slot_bytes - 8192` 이하로 유지한다. 캐시 정책을 쓸 때는 범위가 블록
경계를 걸치지 않아야 한다. 위반 시 `-E2BIG`. 비동기 API는 현재 `GTIER_CACHE_NONE`만 지원한다.

```bash
nvcc -O3 -std=c++17 -arch=sm_110 myapp.cu libgtier.a -luring -lcufile \
  -I/usr/local/cuda/targets/sbsa-linux/include \
  -L/usr/local/cuda/targets/sbsa-linux/lib -o myapp
```

### 7.4 측정 재현

```bash
sudo jetson_clocks
nvpmodel -q
```

**주의:** 테스트 파일은 반드시 **실제 데이터**여야 한다. `ftruncate`로 만든 희소 파일은 구멍을
읽을 때 커널이 디스크를 건드리지 않고 제로 페이지를 할당하므로, 스토리지가 아니라 페이지 할당을
측정하게 된다.

```bash
openssl enc -aes-256-ctr -pass pass:gtier -nosalt < /dev/zero 2>/dev/null \
  | dd of=/tmp/real32.bin bs=64M count=512 iflag=fullblock oflag=direct
du -h --apparent-size /tmp/real32.bin && du -h /tmp/real32.bin   # 둘이 같아야 함
```

```bash
cd lib
./run_bench.sh --file /tmp/real32.bin --item 65536 --n 64 --iters 64     # 백엔드 비교
./gtier_bench --file /tmp/real32.bin --item 65536 --n 64 --slots 64 \
  --policy 3 --reuse 128 --iters 256 --only 0                            # 상주 정책
./run_pipe.sh --file /tmp/real32.bin --item 1048576 --n 16 --iters 64 --policy 0
```

실제 모델:

```bash
./gguf_bench $(for f in /path/to/model/*.gguf; do echo --shard $f; done) \
  --backend 0 --policy 0 --tokens 1 --slot 1048576 --slots 576 --async 1

# MoE 라우팅 반영
./gguf_bench $(...) --backend 0 --policy 0 --tokens 1 --slot 1048576 \
  --slots 576 --async 1 --experts 128 --active 8 --skew 1.0
```

`--backend` 0=gtier, 1=mmap-gpu, 2=mmap-cpu, 3=pread+copy, 4=cufile, 5=uvm.
`--policy` 0=NONE, 1=BLOCK, 2=HYBRID, 3=ADAPTIVE, 4=PIN.
`--batch` 한 스텝이 동시에 처리하는 시퀀스 수. 층마다 그만큼 라우팅을 뽑고 **합집합**을 한 번
읽으므로 토큰당 바이트가 준다(§A4.14). `--experts`/`--active`/`--skew`는 라우팅 분포다.

**safetensors도 같은 드라이버로 읽는다.** `--shard`에 `.safetensors`를 주면 된다 —
`gguf_load`가 매직을 보고 [`lib/safetensors.c`](lib/safetensors.c)로 위임한다. 모델을
변환하지 않고 추론 엔진이 실제로 여는 파일을 그대로 겨눌 수 있다.

```bash
M=/path/to/Qwen3-30B-A3B
SH=$(for f in $M/model-*.safetensors; do echo --shard $f; done)
./lib/gguf_bench $SH --backend 0 --async 1 --batch 8 --tokens 32 \
  --experts 128 --active 8 --skew 0.8 --slot $((4*1024*1024)) --slots 512
```

### 7.5 공정한 비교를 위한 두 가지 계측

**메모리 예산 고정.** 페이지 캐시를 쓰는 백엔드는 예산을 묶지 않으면 캐시 크기로 이긴다.

```bash
./scripts/run_hf_moe.sh                      # 전 백엔드, cgroup 예산 고정
BUDGET=12G TOKENS=8 ./scripts/run_hf_moe.sh  # 예산을 바꿔가며
```

**회수 불가능한 발자국.** RSS는 `cudaMalloc`을 빠뜨리고 `cudaMemGetInfo`는 매핑된 호스트
메모리를 중복 계수한다(§A4.15). `MemAvailable` 하락폭이 유일하게 일관된 값이다.

```bash
./scripts/memfoot.sh ./lib/gguf_bench $SH --backend 4 --batch 8 --tokens 16 ...
# -> MEMFOOT_GIB=10.62
```

**추론 엔진과의 비교.** `/proc/<pid>/io`의 `read_bytes`는 페이지 캐시 적중을 세지 않으므로,
트레이스 드라이버·추론 엔진·llama.cpp 포크에서 모두 같은 뜻을 갖는 유일한 숫자다.

```bash
./scripts/io_meter.py --label moe-infinity --drop-caches -- <command>
```
