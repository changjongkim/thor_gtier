# E2 (부분) — 모델이 안 들어갈 때 무슨 일이 일어나는가

**상태:** 부분 결과. 실제 >122 GiB 모델 대기 중.
**측정일:** 2026-09-22 · 하네스 [`../bench/e2_oversub.sh`](../bench/e2_oversub.sh)

## 방법과 그 한계

실제 오버서브스크립션 모델(Qwen3-235B-A22B Q4_K_M, 132.4 GiB) 다운로드를 기다리지 않기 위해
cgroup v2 `MemoryMax`로 메모리를 모델보다 작게 제한해 체제를 에뮬레이션하려 했다.

> ⚠️ **이 에뮬레이션은 GPU 경로에 유효하지 않다.** 8 GiB 상한에서 14.6 GiB 모델이 `-ngl 99`로
> 정상 동작했다(tg 15.77 t/s). 즉 **Tegra의 `cudaMalloc` 할당은 프로세스 memory cgroup에
> 회계되지 않는다.** 반면 `cudaMallocManaged`는 회계되어 OOM-kill된다. 이 비대칭 때문에
> cgroup 상한은 페이지 캐시와 익명 메모리만 제한하며, 실제 DRAM 부족을 GPU 경로에 대해
> 재현하지 못한다. 아래 GPU 행은 참고용이고, 결론은 실제 모델로 다시 내야 한다.

## 결과 (Qwen2.5-14B Q8_0, 14.6 GiB)

`pp128` / `tg32`, `-r 1`, 실행마다 페이지 캐시 비움.

| 상한 | 모델/상한 | ngl99-cudaMalloc | ngl99-UVM | ngl0-mmap | ngl0-nommap |
|---|---:|---|---|---|---|
| 24 GiB | 0.61x | OK pp=763 tg=15.9 | OK pp=494 tg=15.2 | OK pp=351 tg=5.5 | OK pp=380 tg=5.7 |
| 12 GiB | 1.22x | OK pp=499 tg=15.8 ⚠️ | **FAIL** | OK pp=104 tg=5.0 | **FAIL** |
| 8 GiB | 1.82x | OK pp=495 tg=15.8 ⚠️ | **FAIL** | OK pp=77 tg=5.3 | **FAIL** |

⚠️ = cgroup 회계를 빠져나간 것이므로 유효한 오버서브스크립션 결과가 아님.

## 유효한 관찰

cgroup에 실제로 구속된 경로들에서는 의미 있는 신호가 나온다.

- **`--no-mmap`은 모델보다 작은 메모리에서 아예 실패한다.** 전체를 익명 메모리에 올려야 하므로
  당연하지만, **DRAM을 초과하는 모델에 대해 이 경로는 존재하지 않는다**는 점을 확정한다.
- **UVM(`cudaMallocManaged`)도 실패한다.** 제한 없이는 정상 동작하므로(pp 695.94, tg 13.19)
  구현 문제가 아니라 오버서브스크립션 시 축출할 곳이 없어서다 — 이 플랫폼에는 **swap이 0**이다.
  UVM 페이지 마이그레이션에 기반한 베이스라인(DeepUM 계열)은 여기서 성립하지 않는다.
- **mmap만 살아남되 prefill이 무너진다.** pp 351 → 104 → 77, **4.6배 저하**. 반면 decode(tg)는
  5.5 → 5.0 → 5.3으로 거의 불변이다. prefill은 가중치를 대량으로 훑어 페이징에 노출되고,
  decode는 이미 다른 병목에 걸려 있기 때문으로 보인다.

## 다음

실제 Qwen3-235B-A22B Q4_K_M (132.4 GiB, 1.09x DRAM)이 준비되면 cgroup 없이 그대로 측정한다.
그때 검증할 주장은 다음과 같다.

> DRAM을 초과하는 모델에 대해 이 플랫폼에는 **GPU를 쓰는 경로가 존재하지 않는다.**
> `cudaMalloc`은 용량에 막히고, UVM은 축출할 곳이 없어 막히고, mmap+GPU 폴트는
> [`GRANULARITY.md`](GRANULARITY.md)에서 본 대로 장치의 3~4%만 낸다.
> gTier는 그 빈자리를 메운다.
