# 실제 가중치에서의 상주 — 설계 문제인가 워크로드 문제인가

**모델:** Qwen2.5-32B-Instruct Q8_0, 32.42 GiB, 9 샤드, 64 레이어
**측정일:** 2026-09-23 · 토큰 3회 · 슬롯 16 MiB · 실행마다 페이지 캐시 비움
**드라이버:** [`../lib/gguf_bench.cu`](../lib/gguf_bench.cu)

## 질문

실제 가중치 트레이스에서 **0.157 tok/s**(토큰당 6.4초)가 나왔다. 설계가 나쁜가, 워크로드가
그런 것인가? 분해하면 답이 나온다.

```
토큰당 시간 = (토큰당 읽는 바이트) / (달성 대역폭)
```

**달성 대역폭은 5.105 GiB/s이고 장치 상한(O_DIRECT 순차, 실데이터)은 5.59 GiB/s다 — 91%.**
설계 쪽에는 짜낼 것이 없다. 남는 것은 토큰당 32.42 GiB를 읽는다는 사실이며, 그것은 워크로드
정식화의 문제다. 이 모델은 122.8 GiB DRAM에 들어가므로 실제 배포라면 한 번 올리고 상주시킨다.

## 상주가 답이지만 LRU는 이 접근 패턴에서 병리적이다

가중치 스트리밍은 **토큰마다 모델 전체를 한 번 순환 스캔**한다. 이것은 LRU의 최악 케이스다 —
윈도우가 워킹셋보다 작으면 모든 블록이 다시 쓰이기 전에 축출된다.

| 윈도우 (모델 대비) | BLOCK (LRU) tok/s | 히트율 |
|---:|---:|---:|
| 3.5% | 0.1430 | 54.2% |
| 13.9% | 0.1570 | 54.2% |
| 27.8% | 0.1602 | 54.3% |
| 55.5% | 0.1538 | 54.4% |
| 83.3% | 0.1642 | 57.1% |
| **104.1%** | **0.4405** | 84.8% |

**100%가 되기 전까지 이득이 0이다.** (54%대의 히트율은 한 인출 안에서 여러 범위가 같은 블록을
공유하는 데서 오는 것이고, 토큰 간 재사용이 아니다.)

이것이 실제 타겟 케이스에 치명적이다. Qwen3-235B-A22B Q4_K_M은 132.4 GiB로 122.8 GiB DRAM에
**92% 들어간다** — LRU라면 그 92%가 아무 값도 하지 못한다.

## PIN — 순환 접근에는 고정이 맞다

윈도우를 한 번 채우고 **축출을 멈춘다.** 모델의 W/N이 상주하면 히트율도 W/N이 된다.

| 윈도우 | BLOCK (LRU) | **PIN** | PIN 이득 | PIN 히트율 |
|---:|---:|---:|---:|---:|
| 13.9% | 0.1570 | 0.1626 | +4% | 8.7% |
| 27.8% | 0.1601 | **0.1779** | +11% | 20.5% |
| 55.5% | 0.1537 | **0.2190** | **+42%** | 44.1% |
| **83.3%** | 0.1642 | **0.3046** | **+85%** | 66.3% |
| 104.1% | **0.4405** | 0.3999 | −9% | 80.9% |

PIN의 히트율이 윈도우 비율을 따라간다. 100%를 넘으면 LRU가 근소하게 앞서는데, PIN이 축출하지
않는 대신 유지하는 소량의 scratch 예약 때문이다.

> **순환 스캔에서 LRU는 전부 아니면 전무이고, 고정은 비례한다.** 워킹셋의 대부분이 들어가는
> 체제 — DRAM을 근소하게 초과하는 모델 — 가 정확히 그 차이가 가장 큰 곳이다.

## 도중에 고친 두 개의 실제 버그

측정이 구현 결함 두 개를 드러냈고, 둘 다 기록할 가치가 있다.

**① ADAPTIVE가 콜드 스타트를 스래싱으로 오인했다.** 히트율 창 기반 감지기가 첫 패스에서
모두 강제(compulsory) 미스를 보고 캐싱 체제를 이탈한 뒤, 복귀 임계(70%)에 닿지 못해 갇혔다.
윈도우가 모델보다 커도 exact와 같은 성능을 냈다. **수정:** 한 번도 본 적 없는 블록의 미스는
히트율 계산에서 제외한다 — 용량 미스만이 워킹셋이 안 들어간다는 증거다.

**② ADAPTIVE가 쓰지 않는 scratch에 윈도우의 절반을 예약했다.** scratch는 미스를 정확 인출로
서비스하는 HYBRID에만 필요하다. ADAPTIVE는 캐싱 중에는 블록으로 승격하고 멈춘 뒤에는 슬롯을
직접 쓴다. **수정:** HYBRID와 PIN만 예약하며, PIN은 웨이브 간에 재사용하므로 소량이면 된다.

수정 후 ADAPTIVE는 104% 윈도우에서 BLOCK과 일치한다(0.3999 vs 0.4405 → 0.4332 vs 0.4405).

## 결론

| | |
|---|---|
| 달성 대역폭 / 장치 상한 | **91%** — 설계는 병목이 아니다 |
| 토큰당 읽는 바이트 | 32.42 GiB — **워크로드 정식화가 비용이다** |
| 상주 (LRU, 부분) | **이득 0** — 순환 스캔의 LRU 병리 |
| 상주 (PIN, 83%) | **+85%** |
| 상주 (전체, LRU) | **2.9x** |

낮은 tok/s는 설계 결함이 아니라 **상주 없이 순환 스캔을 스토리지에서 돌린 결과**다. 그리고
부분 상주를 쓸모 있게 만들려면 교체 정책이 LRU가 아니어야 한다.
