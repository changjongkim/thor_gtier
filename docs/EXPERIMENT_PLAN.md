# 실험 계획 (v3, 아키텍처 대 아키텍처)

## 원칙

- 비교에 쓰는 모든 수치는 **각 시스템을 장치에서 끝까지 실제로 실행**해서 얻는다. 공통 비용
  모델이나 공통 드라이버로 다른 시스템을 흉내 내지 않는다. 각 시스템은 자기 데이터 경로,
  캐시, 예측, 스케줄링, 파이프라인을 그대로 가진다.
- 모든 시스템이 같은 연산 스택(PyTorch / transformers)을 쓴다. 차이는 아키텍처에서만 난다.
- 이전 판의 드라이버 행렬(`results/MATRIX`, `results/MATRIX3`)은 시스템 비교에 쓰지 않는다.
  정책 분석과 상한 분석의 근거로만 쓴다(§E8).
- 제외: Qwen3-235B(bf16 체크포인트 없음), llama.cpp(연산 스택이 다름).

## 공통 설정

| 항목 | 값 |
|---|---|
| 장치 | Jetson AGX Thor, 통합 메모리 122.8 GiB, NVMe 5.68 GiB/s, swap 없음 |
| 모델 | Qwen3-30B-A3B bf16 (57 GiB, 128 전문가, top-8), Mixtral-8x7B bf16 (87 GiB, 8 전문가, top-2) |
| 워크로드 | LongBench 21 (긴 프롬프트), ShareGPT 24 (대화), MMLU 24 (5-shot). 모든 시스템·모델에 같은 프롬프트 |
| 요청 | 프롬프트 최대 8192 토큰, 생성 32 토큰(MMLU 8), greedy |
| 메모리 예산 | 모델 크기의 25 / 45 / 65%, 그리고 108%(모델이 다 들어가는 기준점) |
| 예산 강제 | 모든 실행을 cgroup `memory.max` = 예산 + 0.5 GiB 안에서. pinned 메모리와 페이지 캐시가 계산된다 |
| 측정 | 요청별 TTFT, TPOT, 요청 시간, SSD 읽기량, cgroup 최대 사용량. 실행 전 페이지 캐시 비움, 한 번에 한 실행 |

## 비교 시스템 (모두 실제 코드)

| 시스템 | 출처 | 핵심 아키텍처 | 모델 |
|---|---|---|---|
| **PHASOR** | 본 연구, transformers 통합(`phasor_hf/`) | 복사 없는 스테이징, 디코드 사용 확률 상주, 층 내 인과 파이프라인 | 둘 다 |
| ZipMoE | ICML'26 공개 코드, Qwen3·Mixtral 이식(`third_party/zipmoe_qwen3_sm110.patch`) | 무손실 비트 필드 압축, 2단 캐시, cache-affinity 스케줄 | 둘 다 |
| MoE-Infinity | 공개 코드 | 활성 행렬(EAM) 예측 프리페치 + 캐시, SSD→호스트→GPU | Qwen3-30B (Mixtral 지원 확인 중) |
| Fiddler | 공개 코드 | 전문가를 호스트 메모리에 두고 CPU 연산 | Mixtral |
| Mixtral-offloading | 공개 코드 | HQQ 양자화 + LRU + 투기 적재 | Mixtral |
| DuoServe-MoE | 공개 코드 확인 중 | 위상별 프리페치(프리필 파이프라인, 디코드 예측기) | 확인 중 |
| FlashMoE* | 코드 비공개 → 같은 스택 위에 논문대로 재구현(재현임을 명시) | 층별 슬롯 + 학습된 축출기 | Qwen3-30B |

Fiddler와 Mixtral-offloading은 모든 전문가를 호스트 메모리에 둔다. 통합 메모리에서는 그 메모리가
예산과 같은 풀이므로 모델 크기 미만의 예산에서는 실행이 실패하거나 성능이 무너질 것으로 예상하며,
그 결과(실행 가능 최소 예산 포함)를 그대로 보고한다.

## 실험

**E1. 메모리 예산에 따른 end-to-end 성능 (주 결과).**
모델 2 × 워크로드 3 × 예산 4 × 시스템. 요청 시간, TTFT, TPOT의 평균과 P50/P99.
그림: 예산(x) 대 요청 시간(y), 시스템별 선, 모델×워크로드 격자.

**E2. 실행 가능 최소 예산.**
각 시스템이 OOM 없이 동작하는 가장 작은 예산을 예산을 줄여 가며 찾는다(모델 크기의 10%까지).
통합 메모리에서 데이터 경로의 숨은 발자국이 이 경계를 정한다.

**E3. 처리량 (배치).**
예산 45%에서 배치 1 / 4 / 8. 토큰 처리량과 요청 지연. 배치를 지원하는 시스템만.

**E4. I/O 분석.**
요청당 SSD 읽기량, 실효 읽기 대역폭(장치 최대 5.68 GiB/s 대비), 캐시 적중률.
PHASOR는 엔진 통계, 다른 시스템은 `/proc/<pid>/io`의 read_bytes.

**E5. 지연 분해.**
PHASOR-HF 안에서 층별로 계측: 전문가 읽기 대기, 전문가 연산, 비전문가 연산(어텐션 등).
프리필과 디코드를 따로. 다른 시스템은 전체 시간만(내부 계측 불가).

**E6. 메모리 사용.**
각 실행의 cgroup 최대 사용량과 예산 대비 비율, 그리고 PHASOR 내부 분해
(비전문가 가중치, 상주 영역, 스테이징 윈도우, KV 캐시).

**E7. PHASOR ablation (PHASOR-HF 안에서 한 요소씩 교체).**
상주 정책: PHASOR ↔ LRU ↔ 누적 횟수 효용. 데이터 경로: 복사 없는 gTier ↔ pread+복사.
층 내 파이프라인: 켬 ↔ 끔. 프롬프트 라우팅 항: 있음 ↔ 없음.
모델 2 × 워크로드 3, 예산 45%.

**E8. 분석 (시스템 비교가 아닌 근거).**
트레이스 재생 시뮬레이션: Belady 상한 대비 적중률, LRU의 층 순서 편향.
라우팅 특성: 프롬프트 합집합(73–98%) → 상주로는 프리필 읽기량을 줄일 수 없다.
데이터 경로 발자국 미시 측정: gTier 1.17x, pread+copy 2.18x, cuFile 5.31x.

**E9. 민감도.**
스테이징 윈도우 0.25–2 GiB, SSD 대역폭 제한(cgroup `io.max`로 1.5 / 3 GiB/s: 더 느린 엣지 저장장치).

## 실행 순서

1. E1 Qwen3-30B: PHASOR, PHASOR(LRU), ZipMoE, MoE-Infinity — 실행 중(`scripts/stage4.sh`)
2. E1 Mixtral: PHASOR, ZipMoE, Fiddler, Mixtral-offloading, MoE-Infinity(지원 시)
3. FlashMoE* 재구현, DuoServe 확인 → E1에 추가
4. E7 ablation, E2 최소 예산, E3 배치, E9 민감도
5. E4–E6는 E1 실행의 기록에서 산출(추가 실행 없음)
