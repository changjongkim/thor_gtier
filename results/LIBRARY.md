# gTier 라이브러리 — 설계와 측정된 planner 규칙

**구현:** [`../lib/gtier.h`](../lib/gtier.h) · [`../lib/gtier.cu`](../lib/gtier.cu) · [`../lib/demo.cu`](../lib/demo.cu)
**측정일:** 2026-09-22 · 실데이터 32 GiB 파일, 실행마다 캐시 비움

## 구조

```
NVMe ──O_DIRECT DMA──▶ cudaHostAllocMapped 윈도우 ──▶ GPU
                       (복사 0회, 페이지캐시 0회)
```

`cudaHostAlloc(cudaHostAllocMapped)` 메모리가 **동시에** (a) NVMe 컨트롤러의 O_DIRECT DMA 대상이고
(b) GPU가 직접 주소 지정하는 메모리다. 드라이브가 GPU가 읽을 메모리에 직접 쓴다. discrete GPU에서는
GPUDirect Storage 없이 불가능하고, 이 플랫폼에는 GDS가 없다(nvfs 0.0, compat 모드).

API는 범위 인출이다 — `gtier_fetch(g, ranges, n, dev_out)` 가 흩어진 바이트 범위들을 받아 각각에
대한 **디바이스 포인터**를 돌려준다. 클라이언트는 LLM 가중치 스트리밍, 양자 상태벡터, 벡터 인덱스,
DB 버퍼풀 등 out-of-core GPU 워크로드 일반이다.

## planner 규칙 — 둘 다 측정에서 나왔다

### 규칙 1 — 고립된 범위를 증폭하지 마라

O_DIRECT 경계(4 KiB)까지만 정렬하고 그 이상 키우지 않는다.
[`GRANULARITY_FLOOR.md`](GRANULARITY_FLOOR.md) 참조: 증폭 이득이 대역폭 이득을 항상 앞지른다.

### 규칙 2 — 인접 범위도 병합하지 마라 (반직관적)

스토리지 시스템의 보편적 조언은 "I/O를 병합하라"이다. **이 장치에서는 모든 큐 깊이에서 손해다.**

인접 범위(간격 = 항목 크기), 64 KiB × 32:

| 임계값 | 요청/인출 | 증폭 | 유효 대역폭 |
|---|---:|---:|---:|
| 병합 없음 | 32.0 | 1.00x | **2.054 GiB/s** |
| 64 KiB | 4.0 | 1.88x | 1.908 (−7%) |
| 256 KiB | 4.0 | 1.88x | 1.776 (−14%) |
| 1 MiB | 4.0 | 1.88x | 1.752 (−15%) |

얕은 큐(n=4)에서도 마찬가지다: 1.046 → 0.782 GiB/s (−25%).

요청 수를 32→4로 줄여도 증폭 1.88배를 이기지 못한다. **깊은 큐에서 요청은 거의 공짜이고 바이트만
값을 한다.** 그리고 얕은 큐에서조차 이 장치의 요청 고정비용이 증폭 비용보다 작다.

### 보정은 모델이 아니라 측정으로

처음에는 파라메트릭 모델(고정 요청비용 + 바이트당 비용)로 임계값을 유도했고 **틀렸다.**
두 점에서 외삽했는데, 이 장치의 대역폭-크기 곡선은 선형도 단조도 아니다 — 랜덤 256 KiB가
1.179 GiB/s로 64 KiB의 4.311보다 느리다. 현재 구현은 **planner 자체를 후보 임계값들에 대해
실제로 돌려보고 유효 대역폭이 최대인 값을 고른다.**

결과: 모든 큐 깊이에서 `gap = 0`을 정확히 선택한다.

| n | auto 보정 | 수동 gap=0 |
|---:|---:|---:|
| 4 | 0.944 GiB/s (amp 1.00x) | 1.046 |
| 8 | 1.424 (1.00x) | 1.461 |
| 32 | 2.036 (1.00x) | 2.054 |
| 64 | 2.326 (1.00x) | 2.378 |

(auto 쪽의 작은 차이는 같은 프로세스 안에서 수행되는 보정 자체의 비용이다.)

## 큐 깊이가 지배적이다

흩어진 64 KiB 범위, 병합 없음:

| 배치 크기 n (= 큐 깊이) | 유효 대역폭 |
|---:|---:|
| 8 | 1.253 GiB/s |
| 16 | 1.698 |
| 32 | 2.101 |
| 64 | 2.585 |
| 128 | **3.060** |

n=128에서 원시 프로브([`GRANULARITY_FLOOR.md`](GRANULARITY_FLOOR.md)의 64 KiB 지점, 3.146 GiB/s)에
도달한다. 즉 라이브러리 오버헤드는 실질적으로 0이며, **클라이언트가 충분히 많은 범위를 한 번에
제출하는 것이 planner 튜닝보다 중요하다.**

## 현재 한계

- `gtier_fetch`는 동기식이다. 제출 후 전부 기다린다. 데모가 인출마다 `cudaDeviceSynchronize`를
  하므로 I/O와 GPU 연산이 직렬화된다 — 깊은 파이프라인은 다음 단계다.
- 상주 캐시가 없다. 매 인출이 장치를 친다. DRAM을 초과하는 모델에서는 **이미 상주한 부분을
  재인출하지 않는 것**이 핵심이 되므로 이것이 다음 구현 항목이다.
