# Results for the paper (state 2026-09-28 05:40)

Numbers: `results/MATRIX5/SUMMARY.md` (regenerated by `scripts/summarize_matrix5.py`). Analyses: `results/ANALYSIS/`.
This page lists what changed in method and design since the paper's Qwen3 E1 commits (09-27 12:55-13:06), and
what is final vs pending.

## Changes that affect numbers already in the paper

1. **Baselines counted the page cache as free memory (fixed 09-26, commit 026fb82).** ZipMoE, FlashMoE* and
   DuoServe* read weights with buffered I/O; up to 86% of FlashMoE*'s reads came from the page cache, which
   MemAvailable counts as free. Every capped run now drops the model files' page cache every 0.2 s
   (`scripts/scrub_cache.py`), equivalent to direct I/O for all systems (PHASOR reads O_DIRECT, unchanged).
   All Qwen3 baseline cells were rerun; FlashMoE* and ZipMoE became 1.3-2.6x slower at 25-65%.
   Old cells: `results/MATRIX5/qwen30b/archive_buffered_page_cache/`.
2. **PHASOR admits prefill-staged units only into free slots (09-26, 25b2868).** Decode admission is
   unchanged (value-based). Qwen3 MMLU 25%: request 15.1 -> 9.6 s, TPOT 568 -> 254 ms. Old PHASOR cells:
   `archive_prefill_admit_by_value/`. `results/ANALYSIS/PREFILL_ADMISSION.md`.
3. **Cap per run = 1.05 x PHASOR's measured peak at the nominal budget** (was budget + 0.5 GiB, below
   PHASOR's own peak). memcal targets unchanged.

## Final (Qwen3-30B-A3B, all workloads)

- E1: PHASOR fastest in every cell (3 workloads x 4 budgets); vs ZipMoE 1.4-4.4x, FlashMoE* 1.0-2.7x
  (smallest at 108%, largest at 25-45%), DuoServe* 3.5-7.9x. Cells marked `(over)` are baselines whose
  peak grew past PHASOR's on longer workloads (ZipMoE on LongBench: 2-3x the target).
- E2 (small budgets, each system at its own setting): all run down to 5%; PHASOR fastest with the
  smallest peak at every budget.
- E3 (batch 4/8 at 45%): PHASOR highest throughput, 1.9-5.1x.
- E5: prefill is compute/overhead bound (I/O wait ~10% of MoE time); decode hit 0.92-0.97.
- E7/E7b at 45% (request time when a part is removed): prefill free-slot rule +25-72%; LRU (value and
  admission) +26-58%, but **LRU with PHASOR's admission only +1-3%** -> the gain is the admission rule,
  not the value function; pread+copy data path (same memory) +3-14%; extra device copy alone +-3%;
  intra-layer pipeline +8-27%; prompt term and selective decode admission ~0.
- E9: window 0.25-1 GiB within 2%; 2 GiB 5-7% slower (arena shrinks).
- MoE-Infinity cannot run within any budget on this device (`results/PREP/MOE_INFINITY.md`).
- CPU cost per data path: `results/CPU_COST.md`.

## Final (Mixtral-8x7B, generality check: MMLU, four bf16 systems)

PHASOR fastest at 25/45/65%: vs ZipMoE 1.44-1.50x, FlashMoE* 1.88-2.41x, DuoServe* 4.66-5.82x.
108% not run: whole model resident exceeds the host safety ceiling. Fiddler cannot run below the model
size; Mixtral-offloading (2-bit HQQ, lossy) 7.7 s at 25% -- a different accuracy class.
FlashMoE* at 25% used 21 GiB vs PHASOR's 27 (352 MB experts make its per-layer slot coarse).

## ZipMoE fidelity (4.1, `results/ZIPMOE_FIDELITY/FIDELITY.md`)

On its own model (Qwen1.5-MoE-A2.7B-Chat) and harness: our runner matches its harness within 0.8% at
20 GB (same prompts, memory). Its paper's caching-vs-LRU/LFU advantage does not reproduce on Thor
(ZipMoE -1.6% to +10.1% vs LRU/LFU at 10-30 GB).

## Added baselines (queued, 09-28)

- **MoE-APEX\*** (ASPLOS'26, no code released): reimplemented from the paper on the same stack
  (`baselines_hf/apex_hf.py`): LCU caching (eq. 3-4), adaptive prefetch (p = 2). Evaluated with
  precision adaptation off (bf16 mode), so outputs equal the original model like every compared system
  and what is compared is its caching and prefetching -- the same ground on which Mixtral-offloading
  (2-bit) is set apart. The int2 mixed mode is implemented but not run. Stage 7: memcal + Qwen3 E1.
- **FineMoE** (EuroSys'26, bib `yu2026finemoe`): released code with a Qwen3-MoE port
  (`third_party/finemoe_qwen3_sm110.patch`). It loads the checkpoint to CPU and pins every expert in host
  memory (54 GiB for Qwen3-30B) before its GPU cache; on the unified pool it may not serve at all, in which
  case `results/PREP/FINEMOE.md` records why (as for MoE-Infinity). Otherwise: token check, expert maps
  from the other workloads, fidelity against its own measure(), memcal + E1, nominal reference. Stage 8.
