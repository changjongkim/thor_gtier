# LEDGER — 엣지 통합 메모리에서 Out-of-Core MoE LLM 서빙

**LEDGER: Prefill-Aware Expert Residency for Out-of-Core MoE Serving on
Unified-Memory Edge Devices**

**플랫폼:** NVIDIA Jetson AGX Thor · JetPack 7.2 / L4T R39.2 · CUDA 13.0 · Blackwell sm_110
· 122.8 GiB 통합 coherent 메모리 · WD SN5000S 1 TB NVMe (PCIe Gen4 x4) · **swap 없음**

> **효용 기반 상주.** 캐시 교체 정책은 하나의 접근 스트림 안에서 최근성(LRU)이나
> 빈도(LFU)로 순위를 매긴다. MoE 서빙의 스트림은 **재사용 구조가 다른 두 위상**으로 되어
> 있다 — 프리필은 합집합을 요청당 한 번 건드리고, 디코드는 좁은 집합을 토큰마다 건드린다.
> LEDGER는 (층, 전문가)마다 두 위상의 **재사용 횟수를 따로 세어 하나의 효용으로 합치고**
> 그 순위로 상주를 결정한다. 두 항의 단위가 같으므로(막아준 인출 횟수) 비교 가능하다.

> **한 문장.** MoE 오프로딩 문헌은 전부 **디코드**를 최적화한다. 실제 라우팅을 측정해 보면
> 층별 인기순으로 88%를 상주시켰을 때 **디코드는 연산 바운드가 되고(I/O 0.2 ms 대 연산
> 0.89 ms) 프리필만 I/O 바운드로 남는다(1.46 s 대 0.55 s).** 프리필 I/O는 뒤따르는 613토큰
> 디코드 전체의 **15배**다. 그리고 프리필에는 기존 무기가 통하지 않는다 — 합집합을 읽으므로
> **무엇이 올지 맞힐 것이 없다.** LEDGER는 그 위상을 겨냥한다.

**도메인.** 메모리 예산이 제약된 coherent 엣지 SoC 위의 **배치형 out-of-core MoE 서빙**.

## 1. 서론

### 1.1 왜 MoE인가 — 엣지가 가능해지는 유일한 구조

Dense 모델을 엣지에 올리려면 파라미터 수만큼 연산도 줄여야 한다. MoE는 그 둘을 분리한다.
Qwen3-235B-A22B는 총 235B인데 토큰당 **22B만 활성**이고, 그 연산은 Thor에서 0.89 ms다.
**연산은 이미 맞는다. 안 맞는 것은 메모리다** — Q4_K_M으로 132.4 GiB인데 기기는 122.8 GiB다.

### 1.2 왜 엣지인가 — 상주율이 희소 자원이 되는 유일한 지점

서버는 VRAM을 더 사거나 GPU를 늘려 샤딩한다. 전부 상주시킬 수 있으므로 **상주율이 다투는
자원이 아니다.** 엣지는 셋 다 불가능하다 — 메모리가 고정이고, 통합되어 있고, swap이 없어
초과가 OOM이다.

```
Qwen3-235B-A22B Q4_K_M  =  132.4 GiB
Thor 통합 메모리        =  122.8 GiB       M/B = 1.08x
```

**M/B ≈ 1이 이 연구의 조건이다.** 전부 스트리밍하는 것도 아니고 전부 상주시키는 것도
아닌 지점에서만, 상주율 1%p가 값을 갖는다.

### 1.3 측정 — I/O는 디코드가 아니라 프리필에 있다

Qwen3-30B-A3B의 라우터 48개에 훅을 걸어 모델이 실제로 고른 top-8을 기록했다
(프롬프트 6개, 디코드 384토큰, **59,520개 라우팅 결정**, §2.3).

층별 인기순으로 88%를 상주시키면:

| 위상 | 미상주 접근 | I/O | 연산 | 지배 |
|---|---:|---:|---:|---|
| **디코드** (토큰당) | 확률질량 **0.06%** | **0.2 ms** | 0.89 ms | **연산 바운드 4.4x** |
| **프리필** (613토큰) | 합집합 미스 **8.0/128** | **1460 ms** | 545 ms | **I/O 바운드 2.7x** |

**프리필 I/O가 뒤따르는 613토큰 디코드 전체 I/O의 15배다.**

이유는 두 위상이 읽는 것이 다르기 때문이다. 디코드는 토큰당 8/128(6.25%)을 읽는데 그것이
인기 있는 쪽에 몰려 있어 상주로 거의 전부 덮인다. 프리필은 프롬프트 전 토큰의 **합집합**을
읽으므로 **인기 없는 전문가까지 건드린다** — 613토큰이면 층당 79.3%다.

### 1.4 선행연구는 디코드를 최적화한다 — 그리고 프리필에는 그 무기가 없다

| 계열 | 대표 | 최적화 대상 | 프리필에서 |
|---|---|---|---|
| 예측 | Pre-gated MoE, SiDA-MoE, ProMoE | 다음 토큰의 전문가를 미리 안다 | **맞힐 것이 없다** — 합집합이 다 온다 |
| 캐싱 | MoE-Infinity, HOBBIT, Klotski, Mixtral-offloading | 인기 전문가 상주 | **각 전문가 1회** — 재사용이 없다 |
| 연산 배치 | Fiddler | 전문가를 CPU에서 계산 | 프리필은 연산량이 커서 CPU가 못 받음 |
| 압축 | EdgeMoE, 양자화 | 전문가를 줄인다 | 유효하나 직교 |

**프리필은 기존 무기가 구조적으로 안 듣는 위상이다.** 예측은 전부 오니까 무의미하고,
캐싱은 각 전문가를 한 번씩만 읽으니 재사용이 없다.

그리고 캐싱 계열에 대해 측정이 하나 더 걸린다. 층 안에서 상위 절반이 트래픽의 **90.2%**를
먹는데, **어느** 전문가가 인기인지는 층마다 달라 전역으로 합치면 **58.4%**로 거의 균등해
보인다(§2.3). **전역 LRU나 전역 인기 캐시는 이 구조를 보지 못한다.**

### 1.5 우리가 다루는 것

프리필 I/O를 줄이는 길은 세 갈래이고, 셋 다 **엔진이 메모리 분할을 제어해야** 가능하다.

```
B (122.8 GiB) = R (상주 가중치) + W (스테이징) + K (KV/배치)

프리필 I/O = (프롬프트 합집합 − R) 바이트 / 전달 대역폭
```

1. **W를 최소로 해서 R을 최대화한다.** W는 모델의 0.9%에서 포화하므로(§4.14) 그 위는
   전부 R에서 훔친 것이다. 측정된 발자국이 선언 윈도우 대비 gTier **1.17x**,
   pread+copy 2.18x, cuFile **5.31x**이고, 이것이 상주율 **6.3%p** 차이로,
   다시 **TTFT 0.66 s** 차이로 번역된다(§1.6).
2. **상주를 층별 인기순으로 채운다.** 전역 순서로는 위 구조를 못 본다.
3. **프리픽스를 조건으로 상주를 고정한다.** 공유 프리픽스 구간에서 라우팅이 **완전히
   동일**하므로(앞 30토큰 100%, §2.3) 그 합집합은 요청마다 같다. 프리필 I/O를
   요청 간에 상환할 수 있다.

### 1.6 데이터 경로가 TTFT로 번역된다

선언 윈도우를 똑같이 2.00 GiB로 주고 회수 불가능한 점유를 재고(§4.15), 남는 메모리를
상주에 돌린다고 하면(K = 4 GiB 고정, 132.4 GiB 모델, 613토큰 프롬프트):

| 데이터 경로 | 대응 선행연구 | 실제 W | R | 상주율 | 프리필 미스 | 읽기 | **TTFT의 I/O** |
|---|---|---:|---:|---:|---:|---:|---:|
| **gTier** | (본 연구) | **2.33** | **116.5** | **88.0%** | **8.0/128** | **8.3 GiB** | **1.46 s** |
| pread+copy | FlexGen, ZeRO-Infinity | 4.35 | 114.5 | 86.5% | 8.8/128 | 9.1 GiB | 1.60 s |
| cuFile | NVIDIA GDS | 10.62 | 108.2 | 81.7% | 11.6/128 | 12.0 GiB | **2.12 s** |

**cuFile은 1.45배 더 읽고 TTFT에 +0.66 s를 더한다.**

> 이 표는 실측 발자국과 실측 라우팅을 결합해 **유도**한 값이다. 실제 엔진에서의
> end-to-end TTFT는 아직 측정하지 못했다(§5).

### 1.7 기여

1. **라우팅 구조의 측정.** 실제 모델의 라우터를 훅해 59,520개 결정을 기록하고 세 가지로
   분해했다 — 층별 대 전역 편향(90.2% 대 58.4%), 순차 지역성(우연의 6.6배), 공유
   프리픽스의 라우팅 동일성(앞 30토큰 100%). **전역 인기 캐시가 왜 실패하는지**가
   여기서 나온다(§2.3).

2. **문제 재정의.** 현실적 상주율에서 **디코드는 연산 바운드가 되고 프리필만 I/O
   바운드로 남는다**(15배). 문헌이 최적화하는 위상이 싼 쪽이다. 그리고 프리필에는
   예측도 캐싱도 구조적으로 듣지 않는다(§1.3, §1.4).

3. **데이터 경로의 메모리 발자국이 TTFT로 번역됨을 보인다.** 통합 풀에서 데이터 경로가
   선언보다 더 쓰는 메모리는 상주율에서 나오고, 상주율은 프리필 읽기량이다 —
   cuFile 5.31x 발자국 → 상주율 −6.3%p → TTFT +0.66 s(§1.6).

4. **통합 메모리에서 발자국을 재는 방법론.** 세 계수기가 서로 다른 것을 센다. cgroup은
   `cudaMalloc`을 과금하지 않고, RSS도 못 보고, `cudaMemGetInfo`는 매핑된 호스트 메모리를
   중복 계수해 합산이 불가능하다. `MemAvailable` 하락폭만 일관된다. 그리고 예산을
   고정하지 않으면 결론이 뒤집힌다 — 같은 mmap-cpu가 0.607 ↔ 5.289 GiB/s다(§4.15).

5. **LEDGER — 재사용 점수.** 상주 유닛의 값어치를 **그것이 막아준 읽기**로 정의하고,
   프리필과 디코드의 **재사용 횟수를 따로 세어 하나의 효용으로 합친다**:
   `U(u) = h_prefill + W·h_decode`. 두 항의 단위가 같으므로(막아준 인출 횟수) 비교 가능하다.
   두 위상이 경쟁하지 않으므로 **트레이드오프가 설계에서 사라진다** — 항을 하나 빼면
   (`per-layer`, `prefix`) 한 축씩만 이기고, 온전한 식은 둘 다 이긴다(§3.4, §4.16e).
   프로파일은 별개 모드가 아니라 **카운트의 초기값**이고, 손잡이 하나가 "아무것도 모름"에서
   "워크로드를 앎"까지 연속으로 움직인다.

6. **프리픽스를 라우팅에서 읽는다.** 공유 프리픽스 구간은 라우팅이 결정적으로 같으므로
   (앞 30토큰 100%), 일치율로 패밀리를 판정한다 — 실제 공유 1.00/0.99/0.98은 핀하고,
   이름만 비슷한 쌍 0.31은 거부하고, 공유 구간을 넘으면 0.83으로 **스스로 포기**한다.
   **공유 범위를 선언할 필요가 없다.** 기존 프리픽스 캐싱은 KV만 재사용한다(§3.5).

7. **음성 결과와 버린 것.** 연산 과잉은 쓸 수 없다 — 양자화된 가중치는 **1.023x**밖에
   압축되지 않는다. 스테이징 윈도우는 모델의 0.9%에서 포화하고 슬롯 크기는 무관하다.
   그리고 만들다 버린 휴리스틱 셋을 기록한다 — "프리필은 빈 공간만", "첫 접촉에 캐시 안 함",
   치환 히스테리시스. **전부 효용 함수가 대체하거나 역효과였다**(§3.6, §4.12, §4.14).

### 1.8 주장하지 않는 것

- **추론 엔진이 아니다.** 바이트 범위 전달 계층과 그 위의 상주 정책이며, 연산·어텐션·
  KV 캐시를 다루지 않는다. 본 저장소의 벤치마크는 **연산을 하지 않는다** — GPU 커널이 64바이트마다 한
  바이트를 더한다.
- **end-to-end TTFT를 측정하지 못했다.** §1.6은 실측 발자국과 실측 라우팅에서 유도한
  값이다. 실제 엔진 통합이 남아 있다.
- **라우팅 측정 표본이 작다.** 프롬프트 6개, 디코드 384토큰, 기술 문서 도메인,
  greedy 디코딩. 상주 순서를 디코드 통계로 **사후에** 정했다. 따라서 상주 효과는
  상한에 가깝다. 다만 프리필/디코드 비대칭은 표본에 둔감한 구조적 결과다.
- **전송 경로 자체의 우위는 넓지 않다.** 유능한 베이스라인 대비 +16.8%다. 값을 하는
  것은 전송 속도가 아니라 **발자국 → 상주율 → 프리필 읽기량** 경로다.

## 2. 배경

### 2.1 플랫폼 — 하나의 풀이 만드는 기회와 제약

| 항목 | 측정값 |
|---|---:|
| GPU STREAM-triad | 250.2 GB/s (이론치 273의 91%) |
| CPU + GPU 동시 | 230.3 GB/s (0.912x) |
| NVMe 링크 | PCIe Gen4 x4 = 이론 7.34 GiB/s |
| **NVMe 실측 최대** (fio 12설정) | **5.682 GiB/s** (1 MiB, 잡 1개, qd 64) |
| bf16 연산 | 49.5 TFLOP/s |
| Swap | **0 B** |

**병목은 링크가 아니라 SSD다.** 그리고 **동시성을 늘리면 오히려 느려진다**(잡 1개 5.682,
4개 5.102). 단일 스트림 qd 64에서 이미 포화한다.

Thor는 `pageableMemoryAccessUsesHostPageTables = 1` 인 최초의 Tegra다.

| | discrete GPU | **Thor** | Orin |
|---|---|---|---|
| GPU 메모리 | 별도 HBM/GDDR | **시스템 RAM과 동일** | 동일 |
| `concurrentManagedAccess` | — | **1** | **0** |
| `pageableMemoryAccess` | — | **1** | **0** |
| GPU가 파일 백업 mmap 접근 | 불가 | **가능** | 불가 |
| GPUDirect Storage | NVMe → VRAM 직접 | **없음** (`nvfs 0.0`) | 없음 |

**(a) 기회.** `cudaHostAlloc(cudaHostAllocMapped)` 메모리는 **동시에** O_DIRECT DMA 대상이고
GPU가 직접 주소 지정하는 메모리다. **Orin에서는 성립하지 않는다** — 이 메커니즘은 Thor
세대의 coherency를 요구한다.

**(b) 제약.** 데이터 경로가 잡는 모든 바이트가 R과 K에서 나오고, swap이 없으므로 초과는
느려지는 것이 아니라 OOM이다.

### 2.2 NVIDIA GDS는 이 플랫폼에 없다

```
cuFile driver: nvfs major=0 minor=0     ← nvidia-fs 커널 드라이버 없음
dstatusflags=0x0  →  GDS supported = 0  ← POSIX compat 모드 (바운스 버퍼)
```

Thor에서 cuFile은 `NVMe → 바운스 → cudaMemcpy → cudaMalloc 버퍼`이며, **그 바운스 버퍼는
호출자가 선언한 윈도우에 계산되지 않는다** — §1.6의 5.31x가 여기서 나온다.

다만 버퍼 등록 자체에는 한계가 없다 — 64 MiB 버퍼 640개, 40 GiB 등록이 정상 동작한다
([`gtier/cufile_limit.cu`](gtier/cufile_limit.cu)).

## 3. 설계

### 3.0 LEDGER의 두 층

```
┌──────────────────────────────────────────────────────────────┐
│ 층 2 — 재사용 점수 기반 상주 (§3.4)                                       │
│   무엇을 메모리에 남길 것인가                                   │
│     U(u) = h_prefill(u) + W · h_decode(u)          │
│   두 위상의 히트를 같은 단위로 세고 그 합으로 순위를 매긴다       │
│   + 공유 프리픽스를 라우팅 일치로 식별해 핀 (§3.5)              │
│   비교: LRU · MoE-Infinity · Mixtral-offloading · Pre-gated   │
├──────────────────────────────────────────────────────────────┤
│ 층 1 — gTier 데이터 경로 (§3.2~3.3)                           │
│   바이트가 어떻게 도착하는가                                    │
│   착륙지가 곧 GPU 포인터 · 정확 인출 · 연속 제출                 │
│   비교: mmap · pread+copy · cuFile · UVM                       │
└──────────────────────────────────────────────────────────────┘
```

| | 층 1 (gTier 데이터 경로) | 층 2 (재사용 점수) |
|---|---|---|
| 정하는 것 | 바이트가 **어떻게** 오는가 | **무엇을** 남기는가 |
| 베이스라인 | mmap, pread+copy, cuFile, UVM | LRU, MoE-Infinity, Mixtral, Pre-gated |
| 대표 결과 | 선언 예산 **1.17x** (cuFile 5.31x) | 요청 **0.848 s** (moe-inf* 1.387) |
| 측정 위치 | §4.7 · §4.13 · §4.15 | §4.16f · `results/SCHEME/` |

**교차 오염을 막는 방법.** 층 2의 베이스라인(`moe-inf*`, `mixtral*`)도 **전부 층 1 위에서**
돌린다 — 그래야 행을 가르는 것이 정책뿐이다. 반대로 층 1 비교는 정책을 고정하고
데이터 경로만 바꾼다. 어느 표에서도 두 기여가 섞이지 않는다.

### 3.1 메모리 분할 — 재사용 점수가 답하는 질문

§1.5의 분할에서 출발한다.

```
B (122.8 GiB) = R (상주 가중치) + W (스테이징) + K (KV/배치)

프리필 I/O = (프롬프트 합집합 − R) / 전달 대역폭
```

- **W는 0.5 GiB(모델의 0.9%)에서 포화한다**(§4.14). 그 위는 전부 R에서 훔친 것이다.
  층 1(§3.2~3.3)의 일은 W를 최소로 유지하면서 장치 대역폭을 다 쓰는 것이다.
- **그러면 남는 질문은 R을 무엇으로 채우느냐**이고, 그것이 §3.4가 답하는 질문이다.

```
 요청 ──▶ ┌──────────────────────────────────────────────────────────┐
          │ § 3.4  재사용 점수       U = h_prefill + W·h_decode│
          │        + § 3.5 프리픽스 식별이 h_prefill 를 키운다       │
          │        → R 을 무엇으로 채울지 정한다                        │
          ├──────────────────────────────────────────────────────────┤
          │ § 3.3  전달 평면       정확 인출 + 연속 제출                 │
          │        → 증폭 1.00x, 장치의 85~97%                        │
          ├──────────────────────────────────────────────────────────┤
          │ § 3.2  스테이징 평면   착륙지가 곧 GPU 포인터                │
          │        → W = 선언값의 1.17x (cuFile 5.31x)                │
          └──────────────────────────────────────────────────────────┘
                                                    ▼  GPU가 직접 역참조
```

아래 각 절은 같은 형태로 읽는다 — **선행연구가 하는 것 → 이 플랫폼에서 깨지는 것 →
설계 → 측정된 이득.**

### 3.2 [구현] 스테이징 평면 — 착륙지가 곧 GPU 포인터

**선행연구.** 스토리지에서 GPU로 가는 길은 둘이다. 호스트 버퍼에 읽고 복사하거나
(FlexGen, ZeRO-Infinity), GDS로 직접 DMA하거나(cuFile).

**깨지는 것.** Thor에는 GDS 커널이 없어 cuFile이 바운스 버퍼로 퇴화하고, **그 버퍼가
선언한 윈도우에 계산되지 않는다**(§2.2). 복사 경로는 복사 자체보다 **버퍼를 두 벌 잡는
것**이 문제다 — 하나의 풀에서 그것은 R에서 빼는 것이다.

**설계.** `cudaHostAlloc(cudaHostAllocMapped)` 슬롯 하나가 동시에 O_DIRECT DMA 대상이고
GPU 주소다. 드라이브가 GPU가 읽을 메모리에 직접 쓴다.

```
discrete + GDS   NVMe ──DMA──▶ VRAM ──▶ GPU                       복사 0, 버퍼 1벌
Thor + cuFile    NVMe ─▶ 바운스 ─▶ cudaMemcpy ─▶ 버퍼 ─▶ GPU      복사 2, 버퍼 2벌+
Thor + pread     NVMe ─▶ 호스트 ─▶ cudaMemcpy ─▶ 디바이스 ─▶ GPU  복사 1, 버퍼 2벌
gTier            NVMe ──DMA──▶ cudaHostAllocMapped ──▶ GPU        복사 0, 버퍼 1벌
```

**이득.** 선언 2.00 GiB 대비 실제 점유 **2.33 GiB (1.17x)**. pread+copy 4.35 (2.18x),
cuFile 10.62 (5.31x)(§4.15). 복사가 사라지는 것은 대역폭이 아니라 **전송당 지연(~20 µs)**
이고 — 복사 대역폭 127 GB/s는 스토리지의 23배다 — **실질 이득은 버퍼를 한 벌만 잡는 것**,
즉 R을 8.3 GiB 더 주는 것이다.

### 3.3 [구현] 전달 평면 — 정확히, 그리고 링을 비우지 않고

**선행연구.** 블록 단위로 읽고 남는 것은 버린다(페이지 캐시, mmap, 블록 캐시). 또는 인접
요청을 병합해 큰 I/O를 만든다.

**깨지는 것.** 이 장치의 대역폭-크기 곡선은 선형도 단조도 아니다 — 랜덤 256 KiB가
1.179 GiB/s로 64 KiB의 4.311보다 느리다. 그래서 증폭은 거의 언제나 손해다(§4.4).
그리고 64 KiB 위에서 랜덤 ≈ 순차(4.311 vs 4.203)이므로 병합할 이유가 없다(§4.5).

**설계 — planner 규칙 둘.**

- **규칙 1: 고립된 범위를 증폭하지 마라.**
- **규칙 2: 인접 범위도 병합하지 마라.** 깊은 큐에서 요청은 거의 공짜이고 바이트만 값을 한다.

보정은 모델이 아니라 측정으로 한다. 파라메트릭 모델로 임계값을 유도했다가 틀렸다
(§4.5); 지금은 planner를 후보 임계값들로 실제 돌려 최선을 고른다.

**설계 — 연속 제출.** `gtier_fetch`는 제출 후 전부 기다려 인출 사이에 큐가 비워졌다.
티켓 기반 `submit`/`wait`이 다음 배치를 먼저 내보내고 이번 것을 거둔다. 티켓은 겹치지
않는 슬롯을 소유하고, CQE의 `user_data`에 티켓 id를 실어 다른 티켓의 완료를 만나도 잃지
않는다.

```c
gtier_ticket t0, t1;
gtier_submit(g, r0, n, &t0);
for (;;) {
    gtier_submit(g, r1, n, &t1);       // 다음 배치를 먼저
    gtier_wait(g, &t0, dev);           // 그다음 이번 것을 거둔다
    consume(dev);
    std::swap(t0, t1);
}
```

**이득.** 증폭 1.00x를 유지하면서 얕은 큐에서 **+31.7%**(배치 8), 깊은 큐에서 +9.8%.
cuFile 대비 1.29x ~ 1.07x(§4.6). 반면 이중 버퍼링은 이득이 없다(0.98~1.01x) — 병목이
드레인이었기 때문이다(§4.12).

**프리필에 특히 맞는다.** 프리필은 합집합을 한 번씩 읽으므로 재사용이 없고, 캐시가 값을
하지 않으며, **정확히 필요한 바이트만 깊은 큐로 밀어 넣는 것**이 전부다. 이 평면이 그것이다.

### 3.4 [LEDGER의 핵심] 위상 인지 효용 — 두 위상의 재사용을 하나로 합친다

**문제.** 프리필을 위한 상주와 디코드를 위한 상주가 **같은 바이트를 서로 다른 척도로
입찰**한다. 하나는 "이 전문가가 얼마나 자주 라우팅되나"를 세고, 다른 하나는 "이 전문가가
공유 프리픽스에 있나"를 센다. 비교할 방법이 없으니 배분이 임의가 된다. 측정하면 정확히
그렇게 나온다 — 예산 40 GiB에서 프리픽스를 핀하면 프리필 I/O가 1.525 → 0.997 s로 내려가는
대신 토큰당 I/O가 6.92 → 36.90 ms로 오른다(§4.16e).

**선행연구가 하는 것.** 캐시 교체 정책은 **하나의 접근 스트림**을 가정하고 그 안에서
최근성(LRU)이나 빈도(LFU)로 순위를 매긴다. MoE 전문가 캐싱(MoE-Infinity, HOBBIT,
Klotski)도 같은 형태다 — 최근/자주 활성화된 전문가를 남긴다.

**여기서 깨지는 것.** MoE 서빙의 접근 스트림은 **재사용 구조가 다른 두 위상**이다.
프리필은 합집합을 **요청당 한 번** 건드리고, 디코드는 좁은 집합을 **토큰마다** 건드린다.
하나의 최근성·빈도 척도는 이 둘을 구분하지 못하므로, 프리필 접근이 디코드 작업집합을
밀어내거나(LRU) 프리필이 아예 반영되지 않는다.

**설계 — 위상별 재사용 횟수를 따로 세어 합친다.** 상주 유닛의 효용은 **그것이 막아준
인출 횟수**이고, 인출은 두 위상 모두에서 일어난다.

```
U(u) = h_prefill(u) + W · h_decode(u)

  u               = (층, 전문가) 하나
  h_prefill(u) = u 를 프롬프트 합집합에 포함한 요청 수     (요청당 1회 절약)
  h_decode(u)   = u 로 라우팅된 디코드 토큰 수              (토큰당 1회 절약)
  W               = 디코드 히트가 미래에 대해 더 말해주는 정도
```

**같은 단위(막은 읽기 횟수)이므로 더할 수 있다.** 한 번 순위를 매겨 채우면 끝이고, 프리픽스
값과 인기 값이 경쟁하지 않는다. 층 경계도 필요 없다 — 점수가 이미 층을 가로질러 비교 가능하고,
층별 구조는 `u`가 (층, 전문가)라는 데서 **자동으로** 나온다.

#### 카운트는 어디서 오는가 — 손잡이 하나

프로파일은 **별개의 모드가 아니라 카운트의 초기값**이다.

| `--profile-weight` | 카운트 시작점 | 이후 |
|---|---|---|
| 0 | 0에서 시작, 첫 요청들이 채운다 | 계속 누적 |
| 0 < w < 1 | 프로파일을 부분적으로 신뢰 | 계속 누적 |
| 1 | 프로파일 숫자에서 시작, 첫 요청 전에 상주를 채운다 | 계속 누적 |

어느 경우든 **같은 카운트가 계속 쌓이므로, 프로파일이 틀렸으면 교정된다.** 서빙 시스템이
워크로드 프로파일로 튜닝하는 것은 일상적이고, 그것을 쓸 수 없을 때도 같은 정책이 동작한다.

측정 (예산 40 GiB, 정상상태):

| `--profile-weight` | io ms/tok | tok/s | 프리필 I/O |
|---:|---:|---:|---:|
| 0 | 5.19 | 37.047 | 0.742 s |
| 0.25 | 4.26 | 38.663 | 0.612 s |
| **1** | **3.22** | **40.728** | **0.594 s** |

#### 어블레이션 — 항을 빼면 무슨 일이 일어나는가

| 정책 | 실제로 하는 일 | 결과 (예산 40) |
|---|---|---|
| `per-layer` | `h_prefill` **항을 뺌** | 토큰당 I/O는 이기고 프리필을 잃음 |
| `prefix` | `h_prefill`을 **무한대로** 만듦 | 프리필은 이기고 토큰당 I/O를 잃음 |
| **LEDGER** | 온전한 식 | **둘 다 이김** |

한 항씩만 쓰면 한 축씩만 이긴다. 트레이드오프는 설계의 성질이 아니라 **식을 쪼갠 결과**였다.

### 3.5 [LEDGER] 프리픽스 식별 — `h_prefill`을 크게 만드는 것

**관찰.** 라우팅은 은닉 상태의 결정적 함수이므로, 공유 프리픽스 구간에서 **선택되는
전문가가 정확히 같다** — 세 요청이 앞 30토큰에서 100% 일치했다(§2.3d). 기존 프리픽스
캐싱(vLLM, SGLang)은 그 구간의 **KV만** 재사용하고, **전문가 작업집합 재사용은 아무도
하지 않는다.**

**그래서 점수에 어떻게 들어오나.** 공유 프리픽스의 합집합은 매 요청 같은 유닛들을 건드리므로
`h_prefill`이 요청 수만큼 쌓인다. **별도 메커니즘이 아니라 효용 함수의 한 항이 커지는 것**이다. 그 위에 두 가지가 더 필요하다.

**(a) 패밀리 판정은 이름이 아니라 라우팅 일치율로.** 같은 텍스트면 같은 전문가가 선택되므로,
프리픽스 구간의 라우팅이 얼마나 일치하는지가 곧 증거다. 임계값 0.90.

| 패밀리 | 일치율 | 판정 |
|---|---:|---|
| sysA / sysB / sysC (실제 공유) | 1.00 / 0.99 / 0.98 | **핀** |
| distinct (이름만 비슷) | 0.31 | 거부 |
| 공유 구간을 넘겨 65토큰까지 | 0.83 | **스스로 핀을 포기** |

**공유 구간의 실제 범위를 선언할 필요가 없다.** 라우팅에서 읽힌다.

**(b) 패밀리가 여럿일 때 축출.** 배포는 시스템 프롬프트를 하나만 쓰지 않는다. 상한을 넘으면
가장 오래 서빙되지 않은 패밀리를 축출하되, **그 패밀리가 단독으로 쥔 유닛만** 버린다 —
다른 살아있는 프리픽스도 쓰는 유닛은 남는다. 한 번만 온 패밀리는 핀하지 않는다.

### 3.6 만들다 버린 것 — 효용 함수가 대체한 휴리스틱들

정직하게 기록한다. 아래 셋은 구현해서 측정했고 **LEDGER에 들어가지 않는다.**

**(a) "프리필은 빈 공간만 가져간다".** 효용 함수가 없을 때는 옳다 — 프리필은 합집합을 한 번
읽고 돌아오지 않는데 순진한 캐시가 그것을 admit하며 디코드 작업집합을 쫓아낸다. 제거하면
예산 16 GiB에서 토큰당 I/O가 369.91 → 121.45 ms다. **그러나 효용 함수가 있으면 해롭다** —
프리필 히트를 세어놓고 그것이 작동하지 못하게 막으므로, 프롬프트가 반복해서 건드리는 유닛이
영영 상주하지 못한다. 측정: 프리필 I/O가 1.343 s에 고정(온전한 식은 0.594). **이 규칙은 값을
모를 때의 대용품이었다.**

**(b) "첫 접촉에 캐시하지 않는다".** 한 번 스친 것으로 캐시가 차는 것을 막는 고전적 규칙인데
여기서는 역효과다 — 2회 요구 시 토큰당 I/O 5.50 → 14.03 ms, 36.8 → 27.7 tok/s. **승인되지
않은 디코드 작업집합은 카운트도 되지 않기** 때문이다.

**(c) 치환 히스테리시스와 디코드 가중치.** 둘 다 거의 움직이지 않는다 — `W`를 64배 쓸어도
36.6 → 37.2 tok/s다. **한계는 순위가 아니라 첫 패스에 매길 카운트가 없다는 것**이고,
그것이 `--profile-weight`가 존재하는 이유다.

### 3.7 [LEDGER] 예산 계약 — 무엇을 약속하고 어떻게 지키는가

**선행연구가 약속하지 않는 것.** 오프로딩 시스템은 버퍼 크기를 설정으로 받지만, 그것이
프로세스 총 점유의 상한이라고 약속하지 않는다. 디스크리트 GPU에서는 초과분이 풍부한
호스트 DRAM에서 나왔으므로 그래도 됐다.

**깨지는 것.** 하나의 풀에서 초과분은 R에서 나오고, R은 프리필 읽기량이다. 그리고 swap이
없으므로 초과는 느려지는 것이 아니라 **OOM이다** — cuFile은 8 GiB 예산에서 실행되지 않는다.

**설계.** gTier가 잡는 것은 슬롯 링 하나뿐이다(`slots × slot_bytes`). 상주 정책은 그 링
안에서 슬롯을 나눠 쓰고, 비동기 티켓도 그 링을 `GTIER_MAX_INFLIGHT`등분해 쓴다.
**세 평면이 같은 예산을 공유한다.**

**계약이 지켜지는지 확인하는 법.** RSS는 `cudaMalloc`을 빠뜨리고, `cudaMemGetInfo`는
매핑된 호스트 메모리를 중복 계수하며, cgroup은 디바이스 메모리를 과금하지 않는다.
`MemAvailable` 하락폭만 일관되다([`scripts/memfoot.sh`](scripts/memfoot.sh), §4.15).

**그리고 지키는 것이 TTFT다.**

```
발자국 1.17x → 상주율 88.0% → 프리필 8.3 GiB → TTFT 1.46 s   (gTier)
발자국 5.31x → 상주율 81.7% → 프리필 12.0 GiB → TTFT 2.12 s   (cuFile)
```

### 4.4 입도 바닥 — 증폭은 손해다

유효 대역폭 = (항목 수 × g) / 경과시간.

| g | 최적 블록 | 최적 유효 대역폭 | 1 MiB 대비 |
|---:|---:|---:|---:|
| 4 KiB | 4 KiB | 0.530 GiB/s | **0.12x** |
| 16 KiB | 32 KiB | 1.410 | 0.33x |
| **64 KiB** | 64 KiB | 3.146 | 0.73x |
| 1 MiB | 1 MiB | **4.324** | 1.00x |

g=4 KiB에서 64 KiB 블록으로 키우면 raw가 8.2배 오르지만 증폭 16배라 유효 대역폭은 **0.51배로
악화**한다. *"큰 블록으로 읽어 대역폭을 얻어라"* 는 순차 접근에서만 맞다.

**함의:** miss가 플래시로 갈 때 희소성 활용 입도에 상한이 생긴다. 전문가(수십~수백 MiB)와
레이어(수백 MiB)는 위에 있고, **PowerInfer의 뉴런(수~수십 KiB)과 KV 페이지는 아래**라 3~8배를 잃는다.

### 4.7 백엔드 비교

**측정의 의미.** 모든 숫자는 **유효 대역폭(GiB/s)** — 호출자가 요청한 바이트 ÷ 경과 시간.

| 백엔드 | 하는 일 | 대응하는 선행 설계 |

| item | n | **gtier** | cufile | pread+copy | mmap-cpu | uvm | mmap-gpu | vs cuFile |

### 4.13 같은 파일 위에서 — MoE-Infinity가 읽는 바로 그 safetensors

### 4.16b 서빙 실험 — 정책, 프리픽스, 위상, 연산 그림자

전체 수치: [`results/SERVE/SUMMARY.md`](results/SERVE/SUMMARY.md) (큐가 채운다) ·
드라이버: [`lib/serve_bench.cu`](lib/serve_bench.cu) ·
큐: [`scripts/run_serving_queue.sh`](scripts/run_serving_queue.sh),
[`...2.sh`](scripts/run_serving_queue2.sh), [`...3.sh`](scripts/run_serving_queue3.sh)

Qwen3-30B-A3B(56.9 GiB)의 **실측 라우팅**을 실제 파일 위에서 재생하며, 하나의 메모리
예산 안에서 상주 정책만 바꾼다. 상주는 실제로 할당한다 — 36 GiB를 쥔다고 말하는 정책은
36 GiB를 낸다. 보고하는 것은 프리필이 I/O를 기다린 시간(TTFT)과 토큰당 그 시간(TPOT)이다.

정책 다섯은 각각 **하나의 결정만** 분리하도록 배열했다.

| 정책 | 무엇이 다른가 |
|---|---|
| `none` | 아무것도 상주시키지 않는다 (바닥) |
| `lru` | 프로파일도 위상 개념도 없는 캐시 |
| `lru+phase` | 위와 **한 줄만 다르다 — 프리필이 admit하지 않는다** (§3.6) |
| `per-layer` | 층별 인기순 정적 상주 (§3.4) |
| `prefix` | 위 + 공유 프리픽스 합집합을 핀 (§3.5) |
| `online` / `online+prefix` | 같은 것을 **프로파일 없이** 관측으로 배운다 |
| `multi-prefix` | 프리픽스 패밀리 여럿 + 핀 상한 + 축출 (§3.5) |

실험은 E1 정책×예산, E2 데이터 경로 발자국을 같은 예산에 과금, E3 프리픽스와 인기 사이의
배분, E4 윈도우 크기, E5 프로파일 없는 온라인, E6 프리픽스 여럿의 경쟁,
**E7 순차 대 연속 배치**, E8 연산 그림자다.

**E7이 §3.6의 전제를 시험한다.** 위상별 재분할은 시스템이 한 번에 한 위상에 있다고
가정하는데, 연속 배치는 그렇지 않다. `--interleave`가 요청을 섞어 그 경계를 측정한다.

**E8이 §3.4의 비동기 승격이 실제로 공짜인지 본다.** 토큰마다 `max(0, I/O − 연산)`을 스톨로
쌓고, 배경 읽기를 그림자 용량 `연산 × 대역폭`과 나란히 보고한다.

### 4.16c 서빙 결과 — 무엇이 실제로 작동하는가

전체 수치는 [`results/SERVE/SUMMARY.md`](results/SERVE/SUMMARY.md)에 있다. 여기서는
각 실험이 결정한 것만 적는다.

**E1 — 위상 규칙은 예산이 조일 때만 값을 한다.** 프리필이 admit하지 않게 하면 예산 16 GiB에서
토큰당 I/O가 369.91 → **121.45 ms (3.05배)** 로 내려간다. 그러나 예산 24 GiB 이상에서는
반대로 손해였다 — 아예 admit을 막으니 아레나가 채워지지 않아 프리필 I/O가 24~48 GiB 전 구간에서
**5.46 s로 평평**했고, 오염을 감수하는 평범한 LRU는 같은 구간에서 2.07 s까지 내려갔다.
**그래서 규칙을 좁혔다 — 프리필은 빈 공간만 가져가고 남의 것은 뺏지 않는다**(§3.6).

**E5 — 프로파일 없는 온라인이 프로파일을 이긴다.** 예산 16 GiB에서 층별 LFU를 관측만으로 배운
`online`이 토큰당 **79.85 ms**, 정적 프로파일 `prefix`가 530.06 ms, 전역 `lru`가 382.28 ms다.
프로파일이 지는 이유는 그 예산에서 **프리픽스 합집합(27.9 GiB)이 상주(12.6 GiB)에 안 들어가는데도
핀을 시도**하기 때문이다. **프리픽스 핀은 예산 인지가 필수다.**

**E6 — 프리픽스 판정은 이름이 아니라 라우팅으로.** 시스템 프롬프트 셋(영·독 포함)을 섞은
트레이스에서 일치율이 sysA 1.00, sysB 0.99, sysC 0.98로 전부 핀되고, 이름만 비슷한 쌍은
0.31로 거부된다. 프리픽스 구간을 넘겨 65토큰까지 늘리면 일치율이 0.83으로 떨어져 **스스로
핀을 포기하고** per-layer로 폴백한다. **공유 구간의 실제 범위를 선언할 필요가 없다.**
그리고 프리픽스를 **미리 아는 것**의 값은 예산 40 GiB에서 프리필 I/O 0.900 s 대 2.234 s로,
**2.5배**다.

**E7 — §3.6의 전제가 필요한 범위는 생각보다 좁다.** 연속 배치를 흉내 내 요청을 교차시키면:

| 정책 | 순차 TPOT | 교차 TPOT | 배수 |
|---|---:|---:|---:|
| `lru+phase` | 32.41 ms | 32.78 ms | **1.01x** |
| `prefix` | 399.62 | 398.25 | 1.00x |
| `multi-prefix` | 64.08 | 279.52 | **4.36x** |

**위상 규칙은 연속 배치에서도 견고하다** — "프리필은 빈 공간만"은 전역 위상을 묻지 않는
지역 규칙이기 때문이다. **깨지는 것은 프리픽스 핀이다** — 교차가 패밀리를 핀 테이블이
안정되는 것보다 빨리 번갈아 오게 한다. 따라서 **순차 요청(static batching) 전제는 §3.5에
필요하고 §3.6에는 필요하지 않다.**

**E8 — 연산 그림자는 워밍업을 가리지 못한다.** 배경 승격이 원하는 바이트가 16.40 GiB인데
그림자 용량은 실제 연산 시간(0.89 ms/토큰)에서 **0.49 GiB**, 20 ms를 가정해도 10.91 GiB다.
스톨은 31.05 → 14.10 s로 줄지만 0이 되지 않는다. **배경 프리페치는 정상상태에서 공짜이고
상주를 채우는 동안에는 아니다.**

### 4.16e 결정판 비교 — 두 위상을 하나의 가치로 놓으면 트레이드오프가 사라진다

전체: [`results/FINAL/SUMMARY.md`](results/FINAL/SUMMARY.md) ·
큐: [`scripts/run_final_queue.sh`](scripts/run_final_queue.sh)

모든 정책을 **하나의 트레이스, 하나의 바이너리**로 다시 돌렸다. 공개된 아이디어도 같은 예산
위의 정책으로 재구현해 넣었다(`*` 표기 — 아이디어의 재구현이지 그 시스템이 아니다).

| 재구현 | 대응 | 핵심 |
|---|---|---|
| `moe-inf*` | MoE-Infinity | 시퀀스 수준 activation set을 우선 보존 |
| `mixtral*` | Mixtral-offloading | LRU + 직전 토큰 기반 투기적 적재 |
| `--lookahead` | Pre-gated MoE | 게이트를 몇 층 앞당기는가 |

#### 예산 40 GiB (상주 36.6 GiB = 전문가의 68%)

| 정책 | 분류 | **TTFT s** | **TPOT ms** |
|---|---|---:|---:|
| `lru` | 기본 | 1.904 | 14.49 |
| `mixtral*` | SOTA 재구현 | 1.912 | 14.37 |
| `moe-inf*` | SOTA 재구현 | 2.053 | 12.99 |
| `lru+phase` | 본 연구 §3.6 | 2.053 | 12.68 |
| `per-layer` | 본 연구 §3.4 | 1.525 | 6.92 |
| `prefix` | 본 연구 §3.5 | 0.997 | **36.90** |
| **`unified`** | **본 연구 §3.7** | **0.670** | **2.67** |

**`per-layer`와 `prefix`는 각각 한 축을 이기고 다른 축을 잃는다** — 프리픽스 핀이 TTFT를
1.525 → 0.997로 내리는 대신 TPOT를 6.92 → 36.90으로 올린다. 둘이 **같은 바이트를 서로 다른
풀에서 입찰**했기 때문이다. 하나의 가치로 합치면(§3.7) **두 축을 동시에 이긴다.**

최강 베이스라인(`moe-inf*`) 대비 **TTFT 3.06배 · TPOT 4.86배**다. 예산 48 GiB에서는
TTFT 1.340 → **0.118 s로 11.4배**가 된다.

#### Lookahead — 프리게이팅은 이 체제에서 값을 하지 않는다

| lookahead | `per-layer` TPOT | `unified` TPOT |
|---:|---:|---:|
| 1 층 | 6.90 ms | 2.69 ms |
| 4 층 | 6.89 | 2.92 |
| 16 층 | 6.81 | 2.65 |
| 전층 | 6.92 | 2.67 |

**전부 오차 범위다.** 라우터의 선택을 미리 아는 것은 **가릴 지연이 있을 때만** 값을 하는데,
깊은 큐와 쓸 만한 상주가 있으면 가릴 것이 없다. Pre-gated MoE 계열이 당기는 레버가 이
체제에는 닿지 않는다.

> 이것은 드라이버의 숨은 가정을 드러내 고친 결과이기도 하다. 원래는 한 토큰의 전 층을 한 번에
> 인출해 **모든 정책에 전층 lookahead를 공짜로** 주고 있었다. 이제 측정 변수다.

#### 교차 도착 — `unified`은 연속 배치에서 열화하지 않는다

| 정책 | 순차 TPOT | 교차 TPOT | 배수 |
|---|---:|---:|---:|
| `per-layer` | 6.92 | 6.76 | 0.98x |
| `prefix` | 36.90 | 36.64 | 0.99x |
| **`unified`** | **2.67** | **2.59** | **0.97x** |

§3.5의 순차 도착 전제는 **정적 프리픽스 핀에만** 필요하고, 통합 가치는 그 전제 없이도
견고하다 — 효용 함수가 위상이 아니라 **유닛당 예상 절약**을 세기 때문이다.

### 4.16f End-to-end — 실제 토큰 레이트

전체: [`results/TOKRATE/SUMMARY.md`](results/TOKRATE/SUMMARY.md) ·
커널: [`lib/moe_ffn.cu`](lib/moe_ffn.cu) · 큐: [`scripts/run_tokrate_queue.sh`](scripts/run_tokrate_queue.sh)

앞의 표들은 전송 초이고 연산은 모델링이었다. `--compute`는 라우팅된 전문가의
feed-forward를 **실제로 실행**하므로 아래는 토큰 레이트다.

#### 예산 40 GiB (상주 36.6 GiB = 전문가의 68%)

| 정책 | 분류 | I/O ms/tok | 연산 ms/tok | **tok/s** | 프리필 I/O s |
|---|---|---:|---:|---:|---:|
| `lru` | 기본 | 12.61 | 23.34 | 27.813 | 1.747 |
| `moe-inf*` | SOTA 재구현 | 11.91 | 24.03 | 27.820 | 1.861 |
| `mixtral*` | SOTA 재구현 | 12.67 | 24.15 | 27.162 | 1.732 |
| `per-layer` | §3.4 | 8.78 | 24.30 | 30.225 | 1.346 |
| `prefix` | §3.5 | 58.38 | 25.27 | 11.954 | **0.868** |
| **`unified`** | **§3.7** | **3.13** | 21.22 | **41.082** | **0.563** |

**최강 베이스라인 대비 1.48배**, 프리필 I/O는 1.861 → 0.563 s로 **3.3배**다.
예산 24 GiB에서는 18.622 대 15.130으로 1.23배이고, 가장 약한 베이스라인(`lru` 2.725)
대비로는 **6.8배**다.

#### 연산을 어떻게 다뤘는가 — 세 가지를 확정해야 했다

**(a) 가중치는 도착한 자리에서 읽는다.** GPU가 `cudaHostAlloc(Mapped)` 메모리를
**254.0 GB/s**로 읽는데, `cudaMalloc` 254.1, managed 258.3이다
([`gtier/mapped_read_bw.cu`](gtier/mapped_read_bw.cu)). **제자리 읽기는 대가가 없다** —
§3.2의 주장이 주장이 아니라 실행으로 확인된다.

**(b) cuBLAS는 맞는 도구가 아니었다.** 디코드 토큰은 벡터 하나가 3.4 GiB의 가중치를
만나는 일이고, 모든 바이트를 한 번 읽고 재사용하지 않으므로 **메모리 바운드**다.
하한은 3.4 GiB / 254 GB/s = **14.4 ms**인데 `cublasGemmBatchedEx`(n=1)가 **59.3 ms**를
썼다 — 하한의 4배이고, 비교하려던 I/O보다 크다. 워프당 한 행을 맡는 손수 쓴 커널이
예산 40에서 **21~24 ms**로 내린다.

**(c) 그래서 두 번 보고한다.** 커널이 튜닝된 것이 아니므로 측정값과 하한에서의 값을
함께 싣는다(위 표의 `tok/s`와 요약의 `하한에서 tok/s`). **연산 커널은 모든 정책에서
동일하므로 행을 가르는 것은 각 정책이 일으키는 I/O다.**

#### 엔진에 주입하는 길은 막혀 있다

llama.cpp의 `--override-tensor`는 텐서 단위인데 **GGUF는 한 층의 전문가를 하나의
텐서로 stack**한다. 따라서 엔진이 허용하는 가장 세밀한 배치는 **층 단위**이고,
§2.3(a)가 요구하는 (층, 전문가) 단위 상주는 **그 인터페이스로 표현할 수 없다.**
드라이버에서 연산을 돌리는 것은 엔진에 없는 입도를 요구하지 않고 같은 숫자에 닿는
길이다.

### 4.16d 실제 엔진 — llama.cpp가 132 GiB 모델에서 280 GiB를 읽는다

전체: [`results/ENGINE/SUMMARY.md`](results/ENGINE/SUMMARY.md) ·
큐: [`scripts/run_engine_queue.sh`](scripts/run_engine_queue.sh)

Qwen3-235B-A22B Q4_K_M(132.4 GiB)을 122.8 GiB 기기에서 `llama-bench`로 돌렸다.
프롬프트 512토큰, 생성 32토큰, 캐시 비움.

| | llama.cpp (`-ngl 0`, mmap) |
|---|---:|
| **TTFT** (512 토큰) | **36.6 s** |
| **TPOT** | **908 ms/토큰** |
| 읽은 양 | **238.1 GiB** |
| 벽시계 | 462 s |

**모델이 132.4 GiB인데 238.1 GiB를 읽는다 — 1.80배다.** 초과분은 전부 쫓겨났다 다시 들어온
같은 페이지다. M/B가 1.08일 뿐인데도 demand paging은 그만큼을 낭비한다.

> **측정 위생.** 이 수치의 첫 판은 엔진 큐와 다른 큐가 동시에 NVMe를 쓰는 동안 잰 것이었고

> 실행이다. 이후 모든 큐는 `flock`으로 직렬화한다([`scripts/queue_lock.sh`](scripts/queue_lock.sh)).

## 5. 정직한 한계와 철회

- **전송 메커니즘의 우위는 큰 입도에서 좁다.** 1 MiB에서 cuFile 대비 1.28배, 4 MiB에서 1.16배다.
  LLM 가중치는 MiB 단위를 읽으므로 실제 운용 구간에서 격차가 작다. **레버는 전송이 아니라
  상주(최대 14x)와 덜 읽기(10x)에 있다.**
- **장치가 상한이다.** SSD 실측 최대 5.682 GiB/s(PCIe는 7.34까지 가능)이고 gTier는 97%에 있다.
  남은 3%는 비동기 경로가 티켓 2개만 써서 GPU 커널이 완전히 가려지지 않는 우리 쪽 결함이다.
- **철회: "cuFile이 큰 윈도우를 못 잡는다".** 직접 시험하니 **64 MiB 버퍼 640개, 40 GiB 등록이
  정상 동작한다.** 앞선 8 GiB 실패는 우리 벤치마크 설정 탓이었다.
- **철회: "비결정적 붕괴".** `ftruncate`가 만든 희소 파일 아티팩트였다
  ([`results/REGIMES.md`](results/REGIMES.md)).
- **정정: zero-copy는 대역폭이 아니라 지연 이득이다.** 복사는 전송당 고정비 ~20 µs이고
  coherent SoC에서 복사 대역폭(127 GB/s)은 스토리지보다 23배 빠르다.
- **철회: "mmap이 선언 윈도우의 6배를 쓴다".** RSS만 본 결과였다. 그 11.98 GiB는 **회수 가능한
  페이지 캐시**이고 커널이 압박받으면 돌려준다. 회수 불가능한 점유는 0.35~0.54 GiB로 전 백엔드
  중 가장 작다. mmap의 실제 약점은 메모리가 아니라, 예산이 조이면 대역폭이 4.535 → **0.607
  GiB/s**로 무너지는 것이다(§4.15).
- **정정: pread+copy는 2.08이 아니라 4.35 GiB**(윈도우의 2.18배). 호스트 스테이징과 디바이스
  버퍼를 둘 다 잡는데 RSS가 후자를 못 본다. **cuFile은 4.04배가 아니라 5.31배**,
  **gTier는 1.04배가 아니라 1.17배**다 — 차이는 CUDA 컨텍스트 비용이고 모든 백엔드가 똑같이 낸다.
- **이 저장소의 벤치마크는 연산을 하지 않는다.** GPU 커널(`consume`)은 64바이트마다 한 바이트를
  더할 뿐 행렬곱도 어텐션도 KV 캐시도 없다. 따라서 보고하는 `tok/s`는 **"이 속도면 토큰당
  가중치를 이만큼 자주 댈 수 있다"**는 뜻이지 실제 추론 처리량이 아니다. 실제 추론은 여기에
  연산 시간이 더 붙는다.
- **탑티어 베이스라인 세 개를 모두 빌드했으나 아직 end-to-end 비교 측정은 하지 못했다.**
  MoE-Infinity는 `Qwen3MoeForCausalLM`을 지원하고 오프로드 저장소까지 구축되지만, 실행이
  네 번 죽었다. 원인은 순서대로 (1) `triton` 부재, (2) **sm_110 커널 부재** — `setup.py`가
  아키텍처를 sm_80/sm_90/sm_120으로 하드코딩해 `_store.so`에 sm_110 큐빈도 PTX도 없었고
  CUTLASS GEMM이 `Error Internal`로 실패했다(`MOE_CUDA_ARCHS` 환경변수를 받도록 패치하고
  PTX 폴백을 넣어 재빌드), (3) **이 기계의 IDE 언어 서버가 반복적으로 81 GB까지 부풀어
  전역 OOM을 일으킴** — 커널 로그의 OOM 네 건 중 세 건이 그것이고 벤치마크는 부수 피해였다,
  (4) cgroup 안에서 CUDA 컨텍스트가 `std::bad_alloc`. (3)을 막기 전에는 재실행해도 같은
  일이 난다.
- **PowerInfer와 FlexGen은 같은 모델로 비교할 수 없다.** 둘 다 Qwen3-MoE를 지원하지 않는다
  (PowerInfer는 자체 ReLU-sparsified GGUF, FlexGen은 OPT 계열만). 같은 파일 비교가 가능한
  것은 MoE-Infinity뿐이고, 나머지 둘은 각자의 네이티브 모델 위에서 돌리되 gTier를 그 동일
  파일에 겨누어야 한다. 모델은 받아두었다(PowerInfer-7B 15 GB, OPT-6.7B 38 GB).
- 빌드 절차와 네 가지 패키징 문제: 앞서
  "sm_110 PyTorch가 없어 불가능"이라고 적은 것은 틀렸다. 넷 다 패키징 문제였고 전부 해결됐다.
  절차는 [`scripts/baselines_setup.sh`](scripts/baselines_setup.sh)와
  [`scripts/torch_env.sh`](scripts/torch_env.sh)에 기록했다.
  - **PowerInfer**는 PyTorch를 쓰지 않는다 — llama.cpp 포크이고
    `-DCMAKE_CUDA_ARCHITECTURES=110`이면 그대로 빌드된다(CMakeLists 기본값이 52/61/70이라
    명시가 필요하다). CUDA 13, `libcublas.so.13` 링크 확인.
  - **PyTorch**: PyPI aarch64 휠이 CPU 전용인 것은 맞지만 NVIDIA Jetson AI Lab 인덱스에 CUDA
    빌드가 있다. `--extra-index-url`을 같이 주면 pip이 버전이 같은 PyPI 휠을 고르므로
    `--no-deps`로 그 인덱스에서만 받아야 한다. SBSA 휠이 NVPL과 cuDSS를 선언 없이 링크하므로
    둘을 `LD_LIBRARY_PATH`에 얹어야 한다. 결과: `torch 2.11.0`,
    `arch_list ['sm_110','sm_121']`, bf16 49.5 TFLOP/s.
  - **FlexGen**: 임포트 이름이 `flexgen`이 아니라 `flexllmgen`이다.
  - **MoE-Infinity**: `moe-store`가 별도 저장소(PyPI에 없음)이고 버전 핀이 어긋나며
    (`~=0.2.1` 요구, main은 `0.0.0` 빌드), CUTLASS 헤더가 번들되어 있지 않고,
    `/usr/local/cuda` 심링크가 13.2를 가리키는데 거기엔 `lib64/libcublas`가 없어
    `cannot find -lcublas`로 링크가 깨진다. 네 가지를 모두 고치면 C++/CUDA 확장 6개
    (`_store`, `_engine`, `_marlin`, `_kv_cache`, `_paged_attn`, `_v4_fp4`)가 정상 빌드된다.
- **PowerInfer는 out-of-core 체제에서 비교할 수 없다.** PowerInfer 형식 모델이 7B(14.11 GiB)와
  70B q4(39.28 GiB)뿐이고 둘 다 122.8 GiB DRAM에 들어간다. 다만 그 희소성 단위가 KiB급이라는
  것은 코드에서 확인된다 — `gpu_idx`/`gpu_bucket`과 `dequantize_mul_mat_*_sparse` 커널이
  FFN 가중치 행렬의 **행 단위**로 접근하며, LLaMA-7B는 모델 차원 4096이므로 한 행이 q4에서
  약 2 KiB다. §4.4의 입도 바닥(64 KiB)보다 한참 아래다.
- **철회: "라우팅 인지가 10배 레버"(§4.11 초판).** 상주 0을 가정한 값이었다. 층별
  인기순으로 88%를 상주시키면 디코드 I/O는 토큰당 0.2 ms로 연산(0.89 ms)보다 작아진다.
  값을 하는 것은 라우팅 인지가 아니라 **상주율**이고, 남는 병목은 **프리필**이다(§4.16).
- **철회: 초판 §1.5의 "8.3 GiB 초과가 읽어야 할 바이트를 53% 늘린다".** 토큰당 바이트가
  `(M−R)`에 비례한다고 가정했는데, 상주를 인기순으로 채우면 스트리밍되는 것은 인기 없는
  전문가이므로 접근 확률이 크기 비율보다 작다. 비율(1.45x)은 살아남았고 절대값이 틀렸다.
  현재 §1.6은 실측 라우팅으로 다시 계산한 값이다.
- **철회: "I/O가 연산의 2475배"(초판 §1.1).** 상주 0을 가정한 값이다. 상주 88%에서는
  디코드가 연산 바운드(4.4x)이고 프리필만 I/O 바운드(2.7x)다.
- **실측 라우팅 표본이 작다.** 프롬프트 6개, 디코드 384토큰, 기술 문서 도메인, greedy
  디코딩, 상주 순서를 디코드 통계로 사후 결정. **상주 효과는 상한에 가깝다.** 프리필/디코드
  비대칭은 표본에 둔감한 구조적 결과다.
- **§3.5(프리픽스 조건부 상주)와 §3.6(위상별 재분할)은 설계만 되어 있고 미구현이다.**
- **MoE 라우팅은 이제 토큰마다 다시 뽑는다**(§4.13). 고치기 전 숫자는 페이지 캐시를 재고
  있었다. 다만 그 체제에서 캐시 정책은 **손해**다 — 적중률 47.2%인데 4 MiB 블록에 3 MiB
  전문가 텐서가 정렬되지 않아 증폭 1.24x가 붙고, 4.321 → 3.547 GiB/s로 느려진다.
- **`gtier_fetch`의 동기 경로는 여전히 큐를 비운다.** 비동기 API가 있지만 캐시 정책과는 아직
  결합되지 않았다(`gtier_submit`은 `GTIER_CACHE_NONE`만 지원).

## 7. 설치 및 사용

### 7.1 요구사항

- NVIDIA Jetson AGX Thor (JetPack 7.2 / L4T R39.2 이상), CUDA 13.0, `sm_110`
- `liburing-dev` (2.5 이상), `gcc`, `nvcc`
- O_DIRECT를 지원하는 파일시스템 위의 NVMe
- 페이지 캐시를 비우려면 passwordless `sudo` (측정 재현용)

```bash
sudo apt install -y liburing-dev
```

### 7.2 빌드

```bash
git clone git@github.com:changjongkim/thor_gtier.git
cd thor_gtier/lib
make                      # libgtier.a, gtier_bench, gguf_bench
make ARCH=sm_87           # 다른 Jetson 세대
```

### 7.3 라이브러리 사용

```c
#include "gtier.h"

gtier_config cfg = {0};
cfg.backend      = GTIER_BACKEND_GTIER;
cfg.slot_bytes   = 1 << 20;            // 측정된 최적 스테이징 크기
cfg.slots        = 64;
cfg.queue_depth  = 64;
cfg.merge_gap    = 0;                  // 측정 결과: 병합하지 않음
cfg.cache_policy = GTIER_CACHE_ADAPTIVE;
cfg.max_fetch_ranges = 32;

gtier *g = gtier_open("model.gguf", &cfg);

gtier_range r[32] = { {off0, len0}, {off1, len1} /* ... */ };
void *dev[32];
gtier_fetch(g, r, 32, dev);            // dev[i] 는 GPU가 바로 읽는 포인터
my_kernel<<<...>>>((const uint8_t *)dev[0], len0);
gtier_close(g);
```

**연속 배치를 내는 클라이언트는 비동기 API를 쓴다** — 큐를 비우지 않아 얕은 깊이에서 최대 31.7% 빠르다.

```c
gtier_ticket t0, t1;
gtier_submit(g, r0, n, &t0);
for (;;) {
    gtier_submit(g, r1, n, &t1);       // 다음 배치를 먼저
    gtier_wait(g, &t0, dev);           // 그다음 이번 것을 거둔다
    consume(dev);
    std::swap(t0, t1);
}
```

**제약.** 한 범위는 하나의 슬롯 안에 들어가야 한다. O_DIRECT 정렬이 양끝으로 최대 4 KiB씩
늘어나므로 범위 길이를 `slot_bytes - 8192` 이하로 유지한다. 캐시 정책을 쓸 때는 범위가 블록
경계를 걸치지 않아야 한다. 위반 시 `-E2BIG`. 비동기 API는 현재 `GTIER_CACHE_NONE`만 지원한다.

```bash
nvcc -O3 -std=c++17 -arch=sm_110 myapp.cu libgtier.a -luring -lcufile \
  -I/usr/local/cuda/targets/sbsa-linux/include \
  -L/usr/local/cuda/targets/sbsa-linux/lib -o myapp
```

### 7.4 측정 재현

```bash
sudo jetson_clocks
nvpmodel -q
```

**주의:** 테스트 파일은 반드시 **실제 데이터**여야 한다. `ftruncate`로 만든 희소 파일은 구멍을
읽을 때 커널이 디스크를 건드리지 않고 제로 페이지를 할당하므로, 스토리지가 아니라 페이지 할당을
측정하게 된다.

```bash
openssl enc -aes-256-ctr -pass pass:gtier -nosalt < /dev/zero 2>/dev/null \
  | dd of=/tmp/real32.bin bs=64M count=512 iflag=fullblock oflag=direct
du -h --apparent-size /tmp/real32.bin && du -h /tmp/real32.bin   # 둘이 같아야 함
```

```bash
cd lib
./run_bench.sh --file /tmp/real32.bin --item 65536 --n 64 --iters 64     # 백엔드 비교
./gtier_bench --file /tmp/real32.bin --item 65536 --n 64 --slots 64 \
  --policy 3 --reuse 128 --iters 256 --only 0                            # 상주 정책
./run_pipe.sh --file /tmp/real32.bin --item 1048576 --n 16 --iters 64 --policy 0
```

실제 모델:

```bash
./gguf_bench $(for f in /path/to/model/*.gguf; do echo --shard $f; done) \
  --backend 0 --policy 0 --tokens 1 --slot 1048576 --slots 576 --async 1

# MoE 라우팅 반영
./gguf_bench $(...) --backend 0 --policy 0 --tokens 1 --slot 1048576 \
  --slots 576 --async 1 --experts 128 --active 8 --skew 1.0
```

`--backend` 0=gtier, 1=mmap-gpu, 2=mmap-cpu, 3=pread+copy, 4=cufile, 5=uvm.
`--policy` 0=NONE, 1=BLOCK, 2=HYBRID, 3=ADAPTIVE, 4=PIN.
`--batch` 한 스텝이 동시에 처리하는 시퀀스 수. 층마다 그만큼 라우팅을 뽑고 **합집합**을 한 번
읽으므로 토큰당 바이트가 준다(§4.14). `--experts`/`--active`/`--skew`는 라우팅 분포다.

**safetensors도 같은 드라이버로 읽는다.** `--shard`에 `.safetensors`를 주면 된다 —
`gguf_load`가 매직을 보고 [`lib/safetensors.c`](lib/safetensors.c)로 위임한다. 모델을
변환하지 않고 추론 엔진이 실제로 여는 파일을 그대로 겨눌 수 있다.

```bash
M=/path/to/Qwen3-30B-A3B
SH=$(for f in $M/model-*.safetensors; do echo --shard $f; done)
./lib/gguf_bench $SH --backend 0 --async 1 --batch 8 --tokens 32 \
  --experts 128 --active 8 --skew 0.8 --slot $((4*1024*1024)) --slots 512
```

### 7.5 공정한 비교를 위한 두 가지 계측

**메모리 예산 고정.** 페이지 캐시를 쓰는 백엔드는 예산을 묶지 않으면 캐시 크기로 이긴다.

```bash
./scripts/run_hf_moe.sh                      # 전 백엔드, cgroup 예산 고정
BUDGET=12G TOKENS=8 ./scripts/run_hf_moe.sh  # 예산을 바꿔가며
```

**회수 불가능한 발자국.** RSS는 `cudaMalloc`을 빠뜨리고 `cudaMemGetInfo`는 매핑된 호스트
메모리를 중복 계수한다(§4.15). `MemAvailable` 하락폭이 유일하게 일관된 값이다.

```bash
./scripts/memfoot.sh ./lib/gguf_bench $SH --backend 4 --batch 8 --tokens 16 ...
# -> MEMFOOT_GIB=10.62
```

**추론 엔진과의 비교.** `/proc/<pid>/io`의 `read_bytes`는 페이지 캐시 적중을 세지 않으므로,
트레이스 드라이버·추론 엔진·llama.cpp 포크에서 모두 같은 뜻을 갖는 유일한 숫자다.

```bash
./scripts/io_meter.py --label moe-infinity --drop-caches -- <command>
```
