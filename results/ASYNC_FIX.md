# 연속 제출 — 인출 사이에 큐를 비우지 않기

**측정일:** 2026-09-23 · 실데이터 32 GiB · 백엔드마다 페이지 캐시 비움
**구현:** [`../lib/gtier.h`](../lib/gtier.h), [`../lib/gtier.cu`](../lib/gtier.cu) — `gtier_submit` / `gtier_wait`

## 결함

`gtier_fetch`는 n개의 읽기를 제출하고 **전부 기다린 뒤** 반환했다. 연속 배치를 내는 클라이언트는
인출 사이마다 **큐 깊이가 0으로 떨어지고** 그동안 장치가 논다. 반면 cuFile은 8개 스레드가 각자
계속 발행하므로 링이 비지 않는다.

그 결과 큰 입도에서 cuFile에 졌다. 앞선 측정에서 1 MiB일 때 gTier 3.816 대 cuFile 3.972였고,
복사를 gTier에 인위적으로 붙여도(3.624) 여전히 cuFile이 앞섰다 — 즉 **격차의 원인은 복사가
아니라 우리 쪽 큐 관리였다.**

## 수정

submit과 wait을 분리해 티켓으로 관리한다. 티켓은 서로 겹치지 않는 슬롯 구간을 소유하고,
완료(CQE)의 `user_data`에 티켓 id를 실어 **한 티켓을 기다리는 도중 다른 티켓의 완료를 만나도
잃지 않고 해당 티켓에 회계**한다.

```c
gtier_submit(g, r0, n, &t0);
for (;;) {
    gtier_submit(g, r1, n, &t1);   // 다음 배치를 먼저 내보내고
    gtier_wait(g, &t0, dev);       // 그다음 이번 것을 거둔다
    consume(dev);
    swap(t0, t1);
}
```

## 효과

1 MiB 항목:

| 배치 n | 동기 | **비동기** | 개선 | cufile | gTier 우위 |
|---:|---:|---:|---:|---:|---:|
| 8 | 3.831 | **5.044** | +31.7% | 3.895 | **1.29x** |
| 16 | 4.210 | **5.126** | +21.8% | 4.432 | **1.16x** |
| 32 | 4.517 | **5.166** | +14.4% | 4.670 | **1.11x** |
| 64 | 4.738 | **5.203** | +9.8% | 4.850 | **1.07x** |

**얕은 큐에서 이득이 가장 크다** — 배치가 작을수록 드레인이 차지하는 비중이 크기 때문이다.
그리고 5.203 GiB/s는 원시 랜덤 프로브(4.984)를 넘고 장치 순차 상한(5.59)에 근접한다.

그것은 이 저장소의 큐 관리 결함이었지 두 접근법의 차이가 아니었다.

## 남는 해석

[`COPY_COST.md`](COPY_COST.md)의 복사 격리 결과는 여전히 유효하다. 복사 자체는 1 MiB에서 4.7%이고
작은 입도에서 17~26%다. 다만 큰 입도에서 두 백엔드가 비슷했던 이유는 "복사가 숨겨져서"가 아니라
**우리가 큐를 비웠기 때문**이었다. 고친 뒤에는 복사 비용이 그대로 격차로 나타난다 —
1 MiB에서 1.28배는 복사 4.7%보다 크며, cuFile의 compat 경로가 바운스 버퍼와 페이지 캐시를
거치는 추가 비용까지 포함한 값이다.
