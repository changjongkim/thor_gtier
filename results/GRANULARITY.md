# 핵심 결과 — GPU demand paging은 페이지 입도에 갇혀 있다

**장비:** Jetson AGX Thor, JetPack 7.2, CUDA 13.0, sm_110, 122.8 GiB 통합 coherent 메모리
**스토리지:** WD SN5000S 1 TB NVMe · **측정일:** 2026-09-22 · 실행마다 페이지 캐시 비움
**프로토타입:** [`../gtier/gtier.cu`](../gtier/gtier.cu) · **NVMe 프로브:** [`../gtier/randread.c`](../gtier/randread.c)

> ⚠️ **측정 타당성 정정.** 초기 프로브는 `ftruncate`로 파일을 만들었는데 이는 **희소 파일**을 만든다
> (apparent 4.0 GiB / allocated **0**). 희소 파일의 구멍을 읽으면 커널이 디스크를 건드리지 않고 제로
> 페이지를 할당하므로, 스토리지 측정이 아니라 페이지 할당 측정이 된다. 아래 모든 수치는
> **실제 비압축 데이터**(AES-CTR 난수, allocated 33 GiB / 65 GiB)로 다시 측정한 값이다.
> 이전 `REGIMES.md`에 기록했던 "비결정적 하드 실패"는 **희소 파일 아티팩트였고 철회한다** —
> 실데이터에서 64 GiB mmap은 죽지 않고, 다만 343초 걸린다.

## 1. 이 NVMe의 입도별 성능

`io_uring`, `O_DIRECT`, 큐 깊이 64, 64 GiB 실데이터 파일에서 2 GiB씩 읽음.

| 블록 | 랜덤 | 순차 |
|---:|---:|---:|
| 4 KiB | 0.558 GiB/s | 0.271 GiB/s |
| 16 KiB | 1.886 GiB/s | — |
| 64 KiB | 4.311 GiB/s | 4.203 GiB/s |
| 256 KiB | 1.179 GiB/s | — |
| 1 MiB | 3.272 GiB/s | 5.302 GiB/s |

두 가지가 따라 나온다.

- **4 KiB는 재앙이다.** 64 KiB 대비 **10~20배** 느리다.
- **64 KiB 이상에서 랜덤 ≈ 순차다** (4.311 vs 4.203). 깊은 큐를 쓰면 NVMe는 지역성을 거의 신경
  쓰지 않는다. ⇒ **MoE의 전문가 단위 흩어진 접근은 그 자체로는 문제가 아니며, 스토리지 레이아웃
  최적화는 이 플랫폼에서 불필요하다.**

## 2. OS 경로 vs 명시적 윈도우

같은 실데이터 파일, GPU는 두 경로에서 동일한 일을 한다(4 KiB당 8바이트 읽기).

| 크기 | 경로 | 시간 | 실효 대역폭 | 장치(6.0 GB/s) 대비 |
|---:|---|---:|---:|---:|
| 32 GiB | OS demand paging (mmap + GPU fault) | 133.4 s | 0.240 GiB/s | 4.3% |
| 32 GiB | **gTier** (1 MiB 슬롯 × 8, io_uring) | **5.88 s** | **5.442 GiB/s** | **97.4%** |
| 64 GiB | OS demand paging | 343.0 s | 0.187 GiB/s | 3.3% |
| 64 GiB | **gTier** (256 MiB × 8) | **11.78 s** | **5.431 GiB/s** | **97.2%** |

**22.8x ~ 29.0x.** gTier는 크기가 2배가 되어도 평평하다.

## 3. 원인 분리 — GPU 폴트에는 커널 readahead가 닿지 않는다

같은 파일, 같은 매핑, 같은 접근 패턴(4 KiB당 8바이트). **누가 폴트하느냐만 다르다.**

| 폴트 주체 | 시간 | 처리량 |
|---|---:|---:|
| **GPU (블록 1024 × 스레드 256)** | 145.6 s | **0.220 GiB/s** |
| CPU 스레드 **1개** | 11.7 s | **2.736 GiB/s** |
| CPU 4개 | 11.1 s | 2.886 GiB/s |
| CPU 8개 | 17.3 s | 1.849 GiB/s |
| CPU 14개 | 13.8 s | 2.324 GiB/s |

> **CPU 스레드 하나가 GPU 전체보다 12.4배 빠르다.**

이것이 원인을 확정한다. 문제는 **mmap이 아니고**, **4 KiB 페이지 자체도 아니고**, **스토리지 장치도
아니다.** 커널의 readahead(`filemap_fault` → `do_async_mmap_readahead`)가 CPU 폴트에는 적용되어
순차 접근을 큰 I/O로 묶어주지만, **GPU 폴트 경로에는 그 기구가 닿지 않는다.** GPU는 페이지를 한 장씩
서비스받고, §1에서 본 4 KiB 재앙 구간에 그대로 떨어진다.

즉 Thor가 새로 준 능력(GPU가 파일 백업 메모리를 직접 페이징)은 **그것을 쓸 만하게 만드는 OS 기구
없이 노출되었다.**

(CPU 스레드 8개에서 처리량이 떨어지는 비단조 구간은 재현 확인이 필요하다.)

## 4. 메커니즘 — 입도이지 기법이 아니다

gTier의 슬롯 입도만 바꾸고 나머지를 고정했다 (32 GiB, 슬롯 8개, 깊이 8).

| 슬롯 | 처리량 | 비고 |
|---:|---:|---|
| **4 KiB** | **0.198 GiB/s** | **OS 경로(0.240)와 사실상 동일** |
| 16 KiB | 0.681 GiB/s | |
| 64 KiB | 2.144 GiB/s | |
| 256 KiB | 4.373 GiB/s | |
| **1 MiB** | **5.442 GiB/s** | 최고 |
| 4 MiB | 5.225 GiB/s | |
| 16 MiB | 5.247 GiB/s | |
| 64 MiB | 5.382 GiB/s | |
| 256 MiB | 5.369 GiB/s | 포화 |

> **입도를 4 KiB로 낮추면 gTier가 OS 경로와 똑같이 붕괴한다.**

따라서 OS 경로가 느린 것은 "OS라서"도, "페이지 폴트라서"도, "io_uring이 아니라서"도 아니다.
**4 KiB 입도에 구조적으로 고정되어 있기 때문이다.** 어떤 메커니즘이든 4 KiB를 주면 무너지고,
1 MiB 이상을 주면 장치의 97%에 도달한다.

**일반화되는 주장:** coherent SoC의 GPU demand paging은 페이지 입도에 갇혀 있으므로, OS나
드라이버를 어떻게 튜닝하든 현대 NVMe 대역폭의 **약 4%를 넘을 수 없다.** 해법은 **GPU의 접근
입도와 스토리지의 접근 입도를 분리**하는 것이며, 그것이 명시적 윈도우가 하는 일이다.

## 5. 반증된 가설 (정직한 음성 결과)

### H-CPU: "coherent SoC에서는 CPU 작업이 공짜가 아니다" — **거짓**

배경 CPU 부하를 걸고 gTier 처리량을 측정했다 (32 GiB, 256 MiB × 8).

| CPU 부하 스레드 | gTier 처리량 | CPU가 소비한 대역폭 |
|---:|---:|---:|
| 0 | 5.273 GiB/s | 0 |
| 1 | 5.351 GiB/s | 9.7 GiB/s |
| 2 | 5.407 GiB/s | 19.3 GiB/s |
| 4 | 5.323 GiB/s | 38.5 GiB/s |
| 8 | 5.376 GiB/s | 77.1 GiB/s |
| 12 | 5.391 GiB/s | 114.5 GiB/s |

CPU가 114.5 GiB/s를 소비해도 gTier 처리량은 변하지 않는다. out-of-core 체제의 병목은
**메모리가 아니라 스토리지**이고, 5.4 GiB/s는 250 GB/s 메모리 대역폭의 2%에 불과해 여유가 넘친다.
FlexGen·LLM in a Flash·PowerInfer가 CPU를 쓰는 설계는 **이 체제에서 여전히 유효하다.**
(단 STREAM 수준으로 메모리 바운드인 워크로드에서는 다르다 — `docs/PLATFORM_NOTES.md`의 0.912x 참조.)

### H-LAYOUT: "MoE의 흩어진 전문가 접근에는 스토리지 레이아웃 최적화가 필요하다" — **거짓**

§1에서 64 KiB 이상 랜덤 ≈ 순차. 전문가 텐서는 MiB 단위이므로 이미 충분히 크다.
